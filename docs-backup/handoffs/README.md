# Agent 交接记录

本目录保存 **按时间追加** 的工程交接日志，记录每一次 agent 工作完成后的真实上下文：改了什么、验到了哪里、下一步该接什么。

它与项目中其它文档的分工：

| 位置 | 角色 | 更新节奏 |
|---|---|---|
| [`docs/constitution.md`](../constitution.md) | 工程宪法，长期不变的最高原则 | 极少修改 |
| [`docs/design/`](../design/) | 终局设计契约（schema、状态机、DTO、CLI 等） | 设计决策变更时同步更新 |
| [`docs/plan/`](../plan/) | 工程蓝图，里程碑级别的实施路径 | Phase 切换时更新 |
| [`docs/task/`](../task/) | 任务分解，Workstream 颗粒度的勾选列表 | 任务推进时勾选 |
| **`docs/handoffs/`** | **append-only 工作日志**，按日期滚动 | 每次交接 |

设计、计划、任务表是"应当如此"，handoffs 是"实际发生了什么"。两套文档相互校验：handoffs 不应改写设计文档的真相源；设计文档不应记录某次具体工作的过程细节。

## 命名规则

- 默认文件名：`YYYY-MM-DD-<slug>.md`
- 同一批交付跨多次提交时，可以合并到同一份记录
- 同日同主题时，允许在**原文件内追加新章节**（append-only，禁止覆盖或删除已写内容）；新增章节必须带新的时间戳子标题并补齐验证结果
- 同日记录较多时，可整理为 `YYYY-MM-DD-daily-rollup.md`

append-only 的具体语义：**文件内追加，不覆盖既有内容**。整个目录随时间只增不减；个别文件可以在首次提交后继续被追加新章节（但不得删行、不得改写历史段落）。

示例：

- `2026-04-19-design-docs-audit.md`
- `2026-04-19-cargo-workspace-skeleton.md`

## 固定格式

所有记录基于 [TEMPLATE.md](./TEMPLATE.md) 编写，必须包含：

1. 元数据：日期 / Agent / 分支 / HEAD / 相关 commit / 状态
2. 工作摘要（一句话说明问题或目标）
3. 影响范围（模块 / 平台 / 额外影响）
4. 关键变更（按主题分组）
5. 验证与验收（自动化 + 手工，逐项写明结果或未执行原因）
6. 结果（是否可合并 / 是否需要继续修复）
7. 风险与后续事项
8. 给下一位 Agent 的备注（继续工作时该看哪几份文件）

## 编写要求

- **事实型**记录，不写空泛总结
- 验证项必须写明：跑了什么、结果如何、未跑的原因
- 工作未提交时写 `commit: pending`
- 修复依赖新 tag / release 才能生效时必须写清楚
- 跨平台或跨 crate 的影响必须显式列出
- 写入 handoff 不替代更新设计文档；如果一次工作同时改了真相源（schema、状态机、DTO 等），handoff 必须明确指出对应文档已同步
