# ADR 0011: decision-run —— typed-decision 影子运行（Phase B）

- 日期：2026-10-31
- 状态：`proposed`
- 决策者：Develata。沿用 ADR 0010 已定：两个 provider、问题按板块配置、shadow 走独立 `decision-run`、
  整个功能可移除；2026-10-31 已批准 §8 的两项不变量 7 例外。ADR 整体待批准
- 前置：[ADR 0010](./0010-typed-decision-capability.md)（Phase A 已合入 main `e0ffdd0`；两家真机探针的通过记录见
  [handoff](../handoffs/2026-10-31-typed-decision-phase-a.md)）
- 评审：Codex（gpt-6-astra，high）两轮。初稿 4 项 BLOCKER（claim 未绑定策略与执行身份、回放材料不足、lease 不覆盖整段工作、
  响应元数据可写入反射的凭据）、8 项 SHOULD_FIX；二稿 1 项 BLOCKER（数据库与本地处理不在期限内）、5 项 SHOULD_FIX
  （小预算下的板块饥饿、策略表主键与 Laya CHECK 的 NULL、旧策略留档不清理、非 JSON 响应的回放例外、请求构造错误的分类）；
  三稿 1 项 BLOCKER（超时包装不能证明 lease 内完成）、4 项 SHOULD_FIX（同秒轮转、留档清理配额、指纹数据通路、外层超时覆盖已知 status）。
  均已对照源码核实，本稿处理；§7 改为"正确性不依赖计时"

## Context

Phase A 只交付了能力层：`crates/decision` 能对一篇文章发一次请求并返回校验后的类型化结果，但没有任何命令调用它。
Phase C 要用真实数据评估这些判断（与人工标注、与生成式 AI 的 `keep_decision` 对比），前提是先有一批按固定策略、
可追溯地跑出来的判断。Phase B 就是这个"影子运行"：只记录，不影响任何现有流程。

ADR 0010 §7 已给出的约束：

- 独立 `decision-run` 子命令，自有表，自有 claim / lease、有界并发、超时、重试上限与预算，双方言迁移；
- 只读文章，不写 `article_ai_results` / `articles.state`，不覆盖 `ai_raw_response`；
- 关闭时不建立任何连接；
- 表须能经新增迁移删除，并在本 ADR 给出删除步骤。

项目已有约束：

- 宪法 §3.2：新能力必须明确属于哪一层，禁止跨层混写；§3.5：新增平级模块，不侵入主干；
- ADR 0002：跨进程任务用数据库行级 claim + lease（`state`、`lease_owner`、`lease_expires_at`、`attempt_count`）；
- ADR 0005：`StoragePool` 枚举，每个 repo 方法按方言分派 SQL；
- non-goals §1.2：不自建 worker pool / 队列；并行靠多实例各自 claim；
- plan/00 §5 不变量 7：所有外部输入能力上可回放，由留档策略控制是否捕获；违反须审批。
  plan/00 §6 的回放驱动：关键外部输入可在脱离外网时重放，现由 `replay --kind={feed,html,ai}` 承担。

现有 `ai-run` 的做法（本 ADR 的参照）：

- task_gen 只看 `articles.state = 'persisted'`，并在同一事务把文章推进到 `ai_pending`；
- claim 是单条 `UPDATE … WHERE id IN (SELECT … ORDER BY id LIMIT n)`，PostgreSQL 加 `FOR UPDATE SKIP LOCKED`；
  板块经 `articles → feed_entries → feed_sources.category_key` 三表 join 得到，`articles` 没有板块列；
- `attempt_count` 在 claim 时自增；retryable 释放用 `CASE WHEN attempt_count >= max THEN 终态 ELSE 'pending'`；
  每次释放都带 `WHERE id = ? AND lease_owner = ?`；
- 运行开始时 reclaim 过期 lease、把预算耗尽的 pending 行终态化；
- 一次 claim 一整批，再按 `[http].concurrent_fetches` 大小的 `JoinSet` 窗口执行；
  某批出现 retryable 失败后不再 claim 下一批（`flows/ai_run/mod.rs` 的 `retryable_deferred`）；
- 工作量只受 `batch_size × max_batches` 约束，且 `max_batches = 0` 表示不限；没有 token / 费用预算，没有进程内退避；
- 先打开存储，再在各板块执行中检查 lease 预算；
- doctor 的健康检查与 deep_scan 不变量把表名写死（`runtime/src/doctor/deep_scan.rs`）。

以上是参照，不是安全性质的证明；本 ADR 在 lease 覆盖、请求计数与凭据保护上比 ai-run 定得更严。

## Decision

### 1. 分层位置与可移除性（骨架决策）

候选：

- (a) 一个新 crate 同时放命令、flow 与 SQL：删除最简单，但把流程协调层与能力执行层写在一起，违反宪法 §3.2。**不采用。**
- (b) 按层各放专用文件，与现有流水线同构：**采用。**

| 层 | 位置 | 内容 |
|---|---|---|
| 指令接口层 | `crates/cli/src/commands/decision_run.rs` | 参数、装配、摘要输出 |
| 流程协调层 | `crates/runtime/src/flows/decision_run/` | `DecisionRunFlow` 与它自己的依赖 struct `DecisionRunDeps`（放在模块内，不进 `context.rs`） |
| 能力执行层 | `crates/storage/src/repo/decision_result{,_sql,_impl}.rs` | 两张表的全部 SQL 与 `DecisionResultState` |
| 能力执行层 | `crates/decision`（已有） | 客户端；本阶段的扩展见 §9 |
| 迁移 | `migrations/{sqlite,postgres}/0006_decision_results.{up,down}.sql` | 建表与索引 |

- 新增依赖边：`runtime → decision`（模块图与 `modules.lisp` 同步）。storage 不依赖 decision：答案与策略快照以 JSON 文本入库，
  序列化在 runtime 完成。
- 现有 flow、表、状态机与 `run` 命令都不改。
- **可移除性比 Phase A 弱**：逻辑全部在专用文件里，但要在约 8 处共享文件删登记行，并永久保留两对迁移文件。
  卸载流程见 §13。

### 2. 状态机放在 storage，不进 domain

- `DecisionResultState`：`pending` → `running` → `succeeded` | `failed`；`running` → `pending`（retryable 计次、退还、
  过期回收）；`pending` 且预算耗尽 → `failed`（扫描终态化）。
- 定义在 `crates/storage/src/repo/decision_result.rs`，不放 `crates/domain/src/state.rs`。
  - 理由：domain 是核心本体对象层（宪法 §3.1）；typed-decision 是可整体移除的辅助实验对象，只被 storage 与这一个 flow 使用。
  - 代价：偏离 ADR 0002 "状态机集中在 domain/state.rs" 的惯例。plan/08 增加一节登记它并注明归属。

### 3. 表结构

#### 3.1 `decision_policies`：策略快照

| 列 | 约束 |
|---|---|
| `policy_version` | `TEXT NOT NULL PRIMARY KEY`，`CHECK (length(policy_version) = 64)`（SQLite 的 TEXT 主键不隐含 NOT NULL，须显式写） |
| `canonical_json` | TEXT NOT NULL：ADR 0010 §6 的规范化策略 JSON 原文 |
| `created_at` | NOT NULL |

- 每次运行开始时，为每个参与板块写入当前策略（已存在即跳过），写入前校验 `SHA-256(canonical_json) = policy_version`。
- 一个策略一行，多个板块或多次运行共用，体量可忽略。

#### 3.2 `decision_results`：一行 = 一篇文章 × 一个策略版本 × 一个执行身份

| 列 | 约束 / 说明 |
|---|---|
| `id` | 主键（SQLite `INTEGER PRIMARY KEY`，PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`） |
| `article_id` | NOT NULL，FK → `articles(id)`（与 `article_ai_results` 相同，无 ON DELETE；当前没有代码删除文章） |
| `category_key` | TEXT NOT NULL，生成任务时由三表 join 写入 |
| `policy_version` | TEXT NOT NULL，FK → `decision_policies(policy_version)` |
| `execution_key` | TEXT NOT NULL，见 §4 |
| `provider` | TEXT NOT NULL，`CHECK (provider IN ('jev', 'laya'))` |
| `requested_model` | TEXT NOT NULL |
| `laya_max_len` | INTEGER；`CHECK ((provider = 'laya' AND laya_max_len IS NOT NULL AND laya_max_len BETWEEN 512 AND 8192) OR (provider = 'jev' AND laya_max_len IS NULL))`（显式 `IS NOT NULL`，否则 Laya + NULL 使表达式为 NULL 而通过） |
| `state` | TEXT NOT NULL DEFAULT `'pending'`，`CHECK (state IN ('pending', 'running', 'succeeded', 'failed'))` |
| `attempt_count` | INTEGER NOT NULL DEFAULT 0，`CHECK (attempt_count >= 0)` |
| `lease_owner` / `lease_expires_at` | 可空；`running` 时由 claim 写入 |
| `answers_json` | 成功时非空（§8） |
| `reported_model` / `routing_model` / `endpoint_origin` | 部署标识；`endpoint_origin` 只含 scheme + host + port |
| `state_sha256` | 实际发送的 `state` JSON 的 SHA-256 |
| `body_chars_sent` / `body_truncated` | 本地按 `max_state_chars` 截断后的字符数，以及是否截断 |
| `provider_truncated` / `state_tokens_dropped` | Laya 的 `usage.truncated` / `state_tokens_dropped`；Jev 为 NULL |
| `input_tokens` / `latency_ms` | 用量与耗时 |
| `raw_response` / `raw_response_expires_at` | 留档的原始 2xx 响应（§8），可空 |
| `raw_response_bytes` / `raw_response_sha256` / `raw_response_withheld` | 2xx 响应体的长度、SHA-256（仅完整读到时）与未保存原文的原因（`not_json` / `credential` / `incomplete`），由客户端计算（§9），可空 |
| `last_error_kind` / `last_error` | `DecisionError::error_kind()` 与固定文本消息（不含 provider 内容） |
| `started_at` / `completed_at` / `created_at` / `updated_at` | 时间戳；SQLite 为 TEXT、PostgreSQL 为 TIMESTAMPTZ，均由应用绑定 UTC 值；`created_at` / `updated_at` NOT NULL |

- 约束：`UNIQUE (article_id, policy_version, execution_key)`，三列均 NOT NULL，因此不会出现含 NULL 的重复组合。
- 索引：`(category_key, policy_version, execution_key, state, id)`（claim 与候选反连接）、`(state, lease_expires_at)`（回收）、
  `(article_id)`、`(raw_response_expires_at)`（留档清理）。

### 4. 执行身份与 claim 绑定

- **`execution_key`** 精确定义：
  - Jev：`jev:{model}`，如 `jev:jev-1.13.0`；
  - Laya：`laya:{model}:{laya_max_len}`，如 `laya:multilingual:2048`。
  - 不含 `base_url`、超时与并发：换部署地址或调参数不会让已判断的文章重跑；部署标识逐行记录，Phase C 可按它分组。
- **一次运行只处理当前身份**：每个板块的当前身份是 `(category_key, policy_version, execution_key)`，由当前配置算出。
  生成、claim、维护扫描都带这三列作为条件，因此当前配置永远不会执行为别的策略或 provider 生成的行。
  claim 返回的行身份再与当前身份比对一次，不一致即退还并以运行时错误中止（防御性检查，正常不可达）。
- **配置切换**（改问题、换 provider / 模型 / `laya_max_len`）：旧身份的 pending 行原样保留、不被执行；
  若以后切回原配置，它们会被继续处理。摘要报告当前板块中"其它身份的 pending 行数"，让积压可见。
- 不同配置的两个实例同时运行时，各自只领取自己的身份，互不干扰。

### 5. 候选与任务生成

- 候选：属于该板块、`created_at >= cutoff`、`state <> 'retired'`、且没有当前身份行的文章：

  ```sql
  SELECT a.id FROM articles a
  JOIN feed_entries fe ON fe.id = a.origin_feed_entry_id
  JOIN feed_sources fs ON fs.id = fe.source_id
  WHERE fs.category_key = $1 AND a.state <> 'retired' AND a.id > $2
    AND <a.created_at >= $3>
    AND NOT EXISTS (SELECT 1 FROM decision_results d
                    WHERE d.article_id = a.id AND d.policy_version = $4 AND d.execution_key = $5)
  ORDER BY a.id ASC LIMIT $6
  ```

- 时间窗口语义：
  - 运行开始时冻结一次 `now`（UTC），`cutoff = floor_to_second(now − window_hours)`，整次运行不变；
  - 下界含等号，不设上界（时钟偏差导致的"未来"文章也算最近）；
  - SQLite 侧按 R3 的约定把列值规整为 UTC 整秒文本（`replace(substr(created_at,1,19),'T',' ')`）再与
    `sqlite_utc_seconds(cutoff)` 比较；PostgreSQL 侧直接与整秒 `cutoff` 比较。cutoff 是整秒，两边对任意亚秒时间的取舍一致。
- 按需生成：只有当板块没有可领取的当前身份 pending 行时才生成，每次最多生成一个窗口的量（§6），`ON CONFLICT DO NOTHING`。
  keyset 游标按本页最后**扫描到**的 id 前进（不是最后插入的 id），整页都冲突时也能前进。
  这样故障运行不会预先堆积大量 pending。
- 不依赖文章的 AI / 发布阶段，只排除 `retired`。时间窗口的作用是首次启用时不把历史文章整批发给付费 API；
  需要补跑时用 `--window-hours` 显式放宽。

### 6. 调度、并发与请求预算

新增 `[decision]` 字段（全部在 decision crate 解析与校验，不进 config crate 的类型）：

| 字段 | 缺省 | 范围 | 作用 |
|---|---|---|---|
| `concurrency` | 2 | 1..=8 | 一个窗口的大小，即同时在途的请求数 |
| `lease_seconds` | 120 | 30..=3600 | 每行的 lease 时长，须满足 §7 的下界 |
| `max_attempts` | 3 | 1..=10 | 每行计次尝试的上限 |
| `max_requests_per_run` | 100 | 1..=10000 | 单次命令发出的请求上限 |
| `window_hours` | 48 | 1..=8760 | 候选窗口 |
| `raw_response` | `on_failure` | 见 §8 | 原始响应留档 |
| `raw_response_ttl_days` | 30 | 0..=3650 | 留档保存天数，0 = 不过期 |

CLI：`decision-run [--category KEY] [--max-requests N] [--window-hours N]`。

- **按窗口领取**：每一步只 claim `min(concurrency, 剩余预算)` 行，立即全部派发，等它们全部结束、逐行释放后才进入下一步。
  一批里不存在"已领取但长时间排队"的行，lease 只需覆盖单行的工作（§7）。
  这是"单实例内对已领取任务的在途请求上限"，不是 worker pool 或队列，不违反 non-goals §1.2；跨实例并行仍靠各自 claim。
  用独立的 `concurrency` 而不是 `[http].concurrent_fetches`：自部署 Laya 的吞吐与通用抓取无关。
- **板块轮转**：按配置顺序轮流，每轮每个板块最多走一步；某板块无事可做或被暂停（§7、§10）后跳过它。预算属于整次命令调用。
  - **首轮保障**：不带 `--category` 运行时，启动检查要求 `max_requests_per_run ≥ concurrency × 有问题的板块数`，
    不满足即以 78 退出（提示调大预算，或用 `--category` 分开调度）。于是每次运行的第一轮都能给每个有积压的板块一个完整窗口，
    持续积压的板块不会互相饿死。
  - 不保存跨运行的轮转状态；首轮之后的剩余预算按配置顺序继续轮转，靠前的板块在剩余部分略占先，这一点是已知且有界的偏差。
- **claim**：与 ai-run 同形——单条 `UPDATE … WHERE id IN (SELECT … WHERE category_key = ? AND policy_version = ?
  AND execution_key = ? AND state = 'pending' AND (lease_expires_at IS NULL OR lease_expires_at < now)
  AND attempt_count < max ORDER BY id LIMIT n)`，PostgreSQL 加 `FOR UPDATE SKIP LOCKED`；`attempt_count` 在 claim 时自增；
  所有释放都带 `WHERE id = ? AND lease_owner = ?`。
- **维护**：运行开始时，对每个当前身份 reclaim 过期 lease、把预算耗尽的 pending 行终态化为 `failed`
  （kind `retry_budget_exhausted`）。留档清理不按身份过滤，单独执行（§8）。
- **请求计数**：一个"请求"是一次 `DecisionClient` 调用。额度在调用客户端前一刻扣减（§7 的步骤顺序），任何退还都不恢复已用额度；
  因最后一次 lease 检查而未调用的行不扣额度。摘要分别报告领取数与调用数。
  每行每次领取至多调用一次客户端，客户端显式关闭 reqwest 的自动重试（§9），因此一次调用至多一次物理发送，
  单次命令的物理发送数 ≤ `max_requests_per_run`。
- **这不是费用上限**：计费按整次评估的输入 token，取决于标题、正文与问题长度；`max_state_chars` 只截正文。
  `input_tokens` 逐行记录并在摘要中合计。参考：handoff 记录的 2026-10-31 Jev 探针（3 道题、约 200 字正文）为 466 token；
  这只是单一样本，不能外推为上限。需要费用硬上限时另行设计。
- 没有进程内 sleep 或退避：重试发生在下一次运行，间隔由外部调度决定。`Retry-After` 只记入事件。

### 7. lease 与时间：正确性不依赖计时

在协作式调度的 async 运行时里，"每行必在 lease 内完成"无法成为硬保证：Tokio 的 timeout 只在 await 点生效，打断不了同步代码；
客户端停止等待也不代表数据库没有提交（SQLx 的 SQLite worker 可能在通知调用方之前已经 COMMIT）。因此本设计把正确性放在
与计时无关的性质上，计时参数只负责让 lease 过期在正常运行中罕见。

**与计时无关的性质**：

1. 每个 `(article_id, policy_version, execution_key)` 至多一行（唯一键）。
2. 释放只在 owner 仍为本实例时生效；行被他人领取后，旧 owner 的写入被拒（owner 条件）。
   lease 已过期但尚未被他人领取时，旧 owner 的写入仍会成功——它对同一身份的结果同样有效。
3. 单次命令的客户端调用数 ≤ `max_requests_per_run`（§6）。
4. 外部调用是"至少一次"：只有 lease 过期后，另一实例才可能再次领取并发送；结果行仍只落一次（1、2）。

**计时设计**（尽力而为，前提见下）：

- 一行的步骤固定为：claim → 读文章并准备请求 → 最后一次 lease 检查 → 扣减调用额度 → 调用客户端 → 释放。
  事件由协调者在窗口结束后统一写，不在单行任务里。
- 每行在 claim 时得到绝对截止时间 `row_deadline = lease_expires_at − 5 s`。
- 存储调用（含连接池 acquire、事务与结果返回）包在客户端侧 `timeout(min(D, row_deadline − now))` 里，D = 5 s；
  PostgreSQL 另在短事务内设 `SET LOCAL statement_timeout` / `lock_timeout`，让服务器也尽早放弃。
- 最后一次 lease 检查：调用前确认 `row_deadline − now ≥ T + D`；不满足则不调用、不扣额度，退还该行，
  并把该板块暂停到本次运行结束（原因 `lease_insufficient`，记事件），避免对同一行反复"领取—退还"而没有进展。
- 客户端调用：把 `call_deadline = min(now + T, row_deadline − D)` 传入客户端（§9）。客户端按剩余时间给这一次请求设 reqwest 的
  per-request timeout，读响应体同样受它约束；已收到非 2xx 状态时，读体超时或中断仍按该 status 归类（ADR 0010 §5），
  不被统一改写为 `Timeout`。不再在客户端外面另包一层 timeout。
- 启动检查：`lease_seconds ≥ T + 3·D + 10`；缺省 T = 10、D = 5 时下界为 35 s，缺省 lease 120 s。
  不满足即以配置错误（78）退出，在打开存储之前完成。这是容量设定，不是证明。
- 超时之后：
  - 客户端调用到期：按 `Timeout` 处理（请求可能已发出，计次）。
  - 存储操作到期：结果**未知**，可能已提交。不推断已回滚或已退还；计入 `storage_timeouts`，本次运行停止；
    该行若仍为 `running`，由 lease 过期后的回收处理。
- owner 条件未命中（释放影响 0 行）：持有权或状态无法确认，不等于检测到 lease 过期。记为 `owner_mismatch`，
  不覆盖他人状态，本次运行停止派发，退出码 1。
- **收尾期限**：中止或预算用完后，协调者最多等待 `lease_seconds` 让在途任务结束；超时则 `JoinSet::abort_all()`，
  计 `drain_timeout`，退出码 1，未结束的行由 lease 回收处理。事件写入在此之后，每条受 D 约束，失败只记日志，
  事件数不超过调用数的常数倍。
- **前提**（工程假设，不是证明）：
  - 同步处理的输入有界：正文 ≤ `max_state_chars`；问题数与长度受 provider 限制，并对两家统一项目上限
    （每板块 ≤ 50 题、每题 instructions ≤ 2000 字符，Jev 原本没有这两项限制）；响应 ≤ 1 MiB。标题长度取决于上游 feed，未设上限。
  - 在这些输入下，规范化、编码、解码与 `answers_json` 构造的耗时远小于上述余量；进程未被长时间挂起；本机时钟单调前进。
  - 前提不成立时，后果限于 lease 过期后的重复调用、结果未知与提早停止，性质 1–4 仍成立。

### 8. 结果、原始响应与回放（不变量 7）

- **`answers_json`**：`{"schema":1,"answers":[…]}`，按问题顺序。由 runtime 用**策略快照中的问题定义**与归一化结果共同构造：
  - noul：`p_yes`、`top_probability`（Laya 才有）；
  - choice：`label`、`probabilities`（label → p 的对象，label 取自问题定义）、`spread_confidence {kind, value}`、`top_probability`；
  - score：`expected`、`probabilities`（下标即档位）、`spread_confidence`、`top_probability`。
  - 题意（instructions、释义、档位名称）在 `decision_policies.canonical_json` 里，经 `policy_version` 外键关联；
    两者合起来即可脱离当时的配置解读每条结果。`schema` 变化时只追加新版本。
- **原始响应**存本表的 `raw_response` 列，不用 `raw_artifacts`：`ArtifactKind` 是 domain 枚举，新增种类会改 domain。
  代价是仓库里出现第二条原始载荷存储路径，清理规则单独定义（见下）。
- 策略 `[decision].raw_response`：
  - `on_failure`（缺省）：只在响应为 2xx 但未通过校验（`InvalidResponse`）时保存——这正是需要排查契约漂移的情况；
  - `always`：每次可安全捕获的 2xx 都保存，供回放；
  - `never`：不保存。
  - "可安全捕获"= 合法 JSON 且通过 §9 的凭据检查，因此列类型为 TEXT。非 JSON 的 2xx（HTML、截断体等）与含凭据的响应
    在任何策略下都不保存原文，只记错误类别、`raw_response_bytes` 与 `raw_response_sha256`，并记 `raw_response_withheld` 事件
    说明原因：非 JSON 内容可能以任意编码（HTML 实体、百分号编码、base64 等）夹带凭据，无法可靠检查。
  - 非 2xx 的错误体一律不保存、不回显（与 ADR 0010 §5 一致）。
- **体量与清理**：响应体上限 1 MiB，单次运行最多新增 `max_requests_per_run × 1 MiB`（缺省 100 MiB）。
  - 保存时写 `raw_response_expires_at = now + raw_response_ttl_days`；`ttl_days = 0` 表示永久保存，此时 expires_at 为 NULL，须显式配置。
  - 每次运行开始时清理，**不按执行身份过滤**（旧策略的留档同样到期清理）：选取 `raw_response IS NOT NULL AND
    raw_response_expires_at < now` 的行，按 expires_at 排序，每批 500 行，把 `raw_response` 与 `raw_response_expires_at`
    一并置 NULL，因此已清理的行不会被再次选中；结果与唯一键保留。
  - 每次运行的清理上限为 `max(1000, 2 × max_requests_per_run)` 行。单次运行新增留档 ≤ `max_requests_per_run`，
    清理能力是它的两倍，积压能被追平；达到上限后仍有过期行时，摘要标记 `raw_gc_backlog`。
- **回放**：decision crate 提供纯离线入口 `revalidate(provider, requested_model, laya_max_len, canonical_policy_json, raw_body)`，
  用冻结的执行参数与策略快照重新执行 Phase A 的全部响应校验，返回与在线调用相同的结果类型；
  并提供 `canonical_json → QuestionSpec` 的解析，与 `canonical_policy` 互为往返（测试锁定）。
  - **本 ADR 申请的两项例外**（不变量 7），已于 2026-10-31 获 Develata 批准：
    1. 回放以库入口加测试的形式提供，不扩展 `replay` 命令（扩展会让该命令依赖这个可移除的功能）；
       脱离外网的命令行重放留待 Phase C 需要时再定。
    2. 只有可安全捕获的响应能回放；非 JSON 与含凭据的 2xx 只留长度与 SHA-256，原文不可回放。

### 9. 对 decision crate 的扩展

- 归一化结果类型增加 `Serialize`；新增 `revalidate` 与策略 JSON 解析（§8）。
- Jev 的问题校验补上项目上限：每板块 ≤ 50 题、每题 instructions ≤ 2000 字符（与 Laya 一致，§7 的前提）。
- `DecisionClient` 改为 `decide(request, call_deadline) -> Exchange { result, raw: Option<RawInfo> }`（截止时间见 §7）。
  - `raw` 只在收到 2xx 时为 `Some`：`RawInfo { bytes, sha256: Option<[u8; 32]>, body: Option<Vec<u8>>, withheld: Option<Withheld> }`。
    完整读到的响应体才有 `sha256`；超限或读到一半中断的响应 `withheld = Incomplete`、`bytes` 为已读字节数、无 `sha256`；
    `body` 只在可安全捕获时为 `Some`，否则 `withheld` 为 `NotJson` 或 `Credential`。长度、摘要与原因都由客户端计算，
    runtime 不接触未通过检查的原文。
  - 非 2xx 或没有收到响应时 `raw = None`。`Exchange` 与 `RawInfo` 的 Debug 不打印字节。
- **凭据反射保护**（在持有 key 的客户端边界完成）：
  - 将要持久化的响应自由文本（`reported_model`、`routing_model`）若包含 API key，整条响应判为
    `InvalidResponse`（"response reflects the credential"），不返回 raw；
  - raw 体先按字节查找 key，再对 JSON 中**每一个**字符串字面量（含对象键；按词法扫描，重复键不会被合并掉）解码转义后查找；
    任一命中即不交出 raw，并记一条 warn 事件；
  - choice label 必须等于问题定义里的选项，score / 概率是数值，二者不构成自由文本。
- 区分错误发生的阶段（错误映射显式按 reqwest 的分类判断，不再"非 timeout 即 Connection"）：
  - `is_builder()`：请求在本地就构造失败、未发出，映射为 `InvalidConfig`（不带原值）。典型是 key 含换行等非法 header 字符；
    为此 `SystemOneClient::new` 先把 `Bearer {key}` 验证为合法 `HeaderValue`，不合法即以 `InvalidConfig` 失败；
  - `is_timeout()` → `Timeout`；`is_connect()` → `Connection`（连接阶段失败，请求未发出）；
  - 其余（发送中或读响应体时断开）→ 新增的 `DecisionError::Transport`（请求可能已发出），retryable。
- 显式 `ClientBuilder::retry(reqwest::retry::never())`：reqwest 0.12.28 默认会对它认为安全的协议级失败自动重发，
  关闭后一次调用至多一次物理发送（§6）。底层 hyper-util 仍会重试尚未写出、因复用已失效连接而取消的请求，
  这不构成重复发送。

### 10. 失败分类、中止与退出码

| 类别 | 情形 | 处理 |
|---|---|---|
| 成功 | — | `succeeded`，写答案与元数据 |
| 单篇、可重试 | `Timeout`、`RequestTimeout`、`Unavailable`、`Server`、`Transport` | 回 `pending` 并计次（到上限即 `failed`）；该板块本次运行暂停，其它板块继续 |
| 单篇、永久 | `InvalidResponse`（含凭据反射）、`PayloadTooLarge`、`ResponseTooLarge`、`Rejected` 且 code 为 `max_tokens_exceeded`；文章不存在（`article_missing`） | `failed` |
| 全局、与文章无关 | `Unauthorized`、`Connection`（未发出）、`RateLimited`、`InvalidConfig`、`InvalidRequest` | 该行回 `pending` 并**退还**本次计次；整个运行停止 |
| 全局、疑似配置 | 其它 `Rejected`、`UnsupportedEncoding`、`HttpStatus`（含 3xx、404） | 该行回 `pending` 并计次；整个运行停止 |
| 基础设施 | claim / 生成 / 维护 / 读文章的存储错误 | 已领取未发送的行退还；整个运行停止 |
| 基础设施 | 释放失败、数据库操作超时（结果未知）、`owner_mismatch`、任务 panic、`drain_timeout` | 不推断该行状态；若仍为 `running`，由 lease 过期回收；整个运行停止 |
| 时间 | 最后一次 lease 检查不通过（§7） | 不调用、不扣额度，退还；该板块暂停到本次运行结束 |
| 防御 | claim 返回的行身份与当前身份不符 | 退还；整个运行停止 |

- 退还：在同一条受 owner 约束的释放语句里清 lease、回 `pending` 并 `attempt_count = attempt_count − 1`（claim 时已加一）。
  因 claim 只领取 `attempt_count < max` 的行，退还后计数回到领取前的值，与终态化扫描不冲突。
- 只有"请求确定未发出或与文章无关"的情形退还。读响应时断开的 `Transport` 计次，避免某篇稳定断流的文章被无限重试。
- "疑似配置"让触发行计次，是为了避免某篇文章确实触发 400 时每次运行都卡在它身上：它最多卡 `max_attempts` 次运行。
- Laya 的 503 可能由输入确定性触发（ADR 0010 §5），因此归入"单篇、可重试"，由尝试上限兜底。
- **中止流程**：停止派发新窗口 → 当前窗口的所有在途任务照常完成并释放（`JoinSet` 必须排空，不得提前 drop；
  收尾期限见 §7，超时则 `abort_all` 并计 `drain_timeout`）→ 写事件 → 汇总。窗口内的行要么已调用客户端，
  要么已因最后一次 lease 检查退还，因此中止时没有"已领取未处理"的行。
- **退出码**按优先级取最高：配置 / 凭据类（`Unauthorized`、`InvalidConfig`、`InvalidRequest`、启动检查失败）→ 78；
  其它全局错误与基础设施错误 → 1；仅有单篇失败或 `RateLimited` → 0（摘要标记 `rate_limited`）。同 ai-run，单篇失败不影响退出码。
- 任何失败都只表示"没有判断"，不得推断为文章不重要（ADR 0010 §5）。

### 11. 命令与可观测性

- `decision-run` 是独立子命令，**不加入 `run`**，部署方另配一条调度。不支持 `--dry-run`（同 ai-run）。
- `[decision]` 缺失或 `enabled = false`：在打开存储与构造客户端之前以退出码 78 结束，不建立任何连接。
  启用时先解析凭据、校验问题、lease 下界与首轮预算（§6），全部通过后才打开存储（写命令会自动执行迁移）。
  这比 ai-run 先开库再检查更早失败。
- run_events：stage `decision_run`；事件 `run_started`、`run_completed`、`decision_completed`、`decision_failed`
  （带 `error_kind`、§10 类别、是否计次）、`decision_run_aborted`、`owner_mismatch`、`lease_insufficient`、`leases_reclaimed`、`retry_budget_swept`、
  `raw_responses_expired`、`raw_response_withheld`；target 为 `("decision_result", id)`。事件里不放文章内容、答案与响应体。
- 摘要（文本与 JSON）：每板块的 generated / claimed / succeeded / failed / retried / refunded / 其它身份 pending 数；
  全局的请求数、input_tokens 合计、`aborted`（类别与 kind）、`budget_exhausted`、`rate_limited`、
  基础设施计数（`storage_errors`、`storage_timeouts`、`release_failed`、`owner_mismatch`、`tasks_panicked`、`drain_timeout`）、
  领取数与调用数、`raw_gc_backlog`、耗时。
- **doctor 不纳入**：健康检查与 deep_scan 不认识这两张表；加进去会让 doctor 依赖可移除的功能。
  lease 回收、预算终态化与留档清理由 `decision-run` 自己在运行开始时完成，状态通过摘要与 run_events 可见。
  这是有意保留的观测缺口；Phase C 若决定让判断参与流程，再连同 doctor 一起设计。

### 12. 测试

- storage（SQLite 进程内；PostgreSQL 走现有 postgres lane）：
  - 候选：窗口边界（亚秒、整秒、混合 SQLite 时间文本）、板块、`retired`、反连接、整页冲突时游标前进；
  - 生成幂等；并行 claim 不相交；claim 只领当前身份（两种身份并存）；错 owner 释放无效；
  - 过期回收、预算终态化与退还交错；退还后计数；留档清理跨身份生效、不重复选中、上限为 `max(1000, 2 × 预算)` 并在积压时标记；
  - 全部 CHECK 与 NOT NULL 拒绝非法行，含 Laya + NULL `laya_max_len` 与 NULL 策略主键。
- flow（假 `DecisionClient`）：
  - §10 每一行的状态变化、计次与退出码，含多个全局错误同时出现时的优先级；
  - 请求预算：多板块、末窗口不足、中止时不超额、退还不恢复额度；两个持续积压板块都能拿到请求；
  - 最后一次 lease 检查不通过（整窗口未发送即退还、板块暂停、不扣额度）、`owner_mismatch`、释放失败、数据库操作超时、panic、
    存储错误；中止时在途任务被排空而非取消；
  - 板块轮转：预算恰为 `concurrency × 板块数` 时每个积压板块每次运行都得到一个窗口；预算不足时以 78 退出；
  - 收尾期限：在途任务超过期限时被 `abort_all`、计 `drain_timeout`、退出码 1；
  - 截止时间传入客户端：准备阶段耗时后收到 401 且错误体停滞，仍归为 `Unauthorized`；
  - 配置切换后不执行旧身份行、切回后继续；`raw_response` 三种策略与 TTL；事件不含正文、答案与响应体。
- decision crate：`answers_json` 固定形状；`Exchange` 只在 2xx 且无凭据时带原始体、Debug 不含字节；
  凭据反射（`reported_model`、`routing_model`、raw 中的转义写法与重复键）；`RawInfo` 的四种形态（可捕获、`NotJson`、
  `Credential`、`Incomplete`）及其长度 / 摘要；Jev 的 50 题与 2000 字符上限；
  `Transport` / `Connection` / builder 错误的区分，含 key 带换行时零发送并以 78 退出；
  `revalidate` 对在线结果的一致性与 `canonical_json` 往返；客户端不自动重试（传输层计数测试）。
- CLI：参数、关闭时退出码 78 且不打开存储、启动检查、摘要 JSON 形状。
- 迁移：pin 与双方言配对测试；新库全链与从 0005 升级。
- 手工验收：对临时 SQLite 库与合成文章，用用户的 Laya 实例跑一次 `decision-run`，只用合成数据。

### 13. 卸载流程

源码删除不会改变已部署的数据库，迁移只在新二进制执行写命令时应用，因此卸载按以下顺序：

1. 停用外部调度中的 `decision-run`，并确认所有 `decision-run` 进程都已退出（以进程确认为准，不能用等待一个 lease 时长代替）。
2. 发布一个"移除版本"，同时包含：
   - 新增前向迁移 `NNNN_drop_decision_results`（取当时下一个可用编号，两方言）：up 为 `DROP TABLE decision_results`、
     `DROP TABLE decision_policies`；down 重建 0006 的空表结构（数据不可恢复，不得在 down 里再次 DROP），并登记 pin；
   - 源码删除：`crates/cli/src/commands/decision_run.rs`；`args.rs` 中的 `Command::DecisionRun`、参数 struct 及其在
     `name()` / `accepts_dry_run()` 的分支；`commands/mod.rs` 的分派行；`context_factory.rs` 的装配函数；
     `crates/runtime/src/flows/decision_run/`、其 `mod` 行与 runtime 中的 re-export；runtime 对 decision 的依赖；
     `crates/storage/src/repo/decision_result*.rs` 与 `repo/mod.rs`、`lib.rs` 的登记行；
   - 再按 plan/18 §1 删除 Phase A，并补上其遗漏项：`crates/config/src/loader.rs` 中调用 `decision::extract` 的一行、
     `crates/cli/tests/validate_config_cmd_tests.rs` 中的 decision 用例。
3. 部署后显式执行 `migrate`，再用会做完整迁移状态检查的只读命令（`ensure_migration_state_exact`：版本、校验和、无多余版本）
   确认状态与二进制一致，并确认两张表已不存在。`migrate check` 主要检查 pending 版本，不能单独作为卸载证据。
4. `0006` 与新的删除迁移文件、以及它们的 pin 必须永久保留：已执行过的数据库记录了它们的校验和。
5. 卸载验收：新库全链迁移；带 Phase B 数据的库升级；重复执行 `migrate` 幂等；其余命令回归通过。
6. 文档：本 ADR 改为 `deprecated`；删 plan/18 的 Phase B 章节、plan/08 的状态机登记、cli-reference 与验收用例、地图条目。

## Consequences

### 正面后果

- 有了可追溯、可离线复核的判断数据：每条结果都能对回策略快照、执行身份、部署标识与实际发送的文本。
- 主流程、现有表与状态机零改动；关闭时零连接。
- 请求数有硬上限且退还不恢复额度；凭据或连接故障不消耗文章的尝试次数；反射的凭据不会落库；
  结果的唯一性与归属不依赖计时（§7 的性质 1–4）。

### 负面后果 / 代价

- 可移除性弱于 Phase A：约 8 处共享文件要删登记行，两对迁移文件永久保留，卸载需要按 §13 的顺序发布与迁移。
- 状态机不在 domain，偏离 ADR 0002 的集中惯例（plan/08 登记弥补）。
- 第二条原始载荷存储路径（`raw_response` 列），有独立的 TTL 清理。
- 按窗口领取在窗口之间有一次同步等待，吞吐低于整批领取；对影子运行可以接受。
- lease 内完成只是尽力而为：前提不成立时可能出现重复调用与"结果未知"（§7）。
- 不带 `--category` 运行要求预算至少覆盖每个板块一个窗口（§6）。
- 回放只有库入口，没有命令行；非 JSON 与含凭据的 2xx 不可回放（§8 的两项例外）。
- doctor 看不到这两张表。
- 启用后 `decision-run` 是第一个真正向 Jev / Laya 发送文章内容的命令；数据外发见 ADR 0010 Consequences，
  费用没有调用前的硬上限（§6）。
