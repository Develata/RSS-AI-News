# ADR 0011: decision-run —— typed-decision 影子运行（Phase B）

- 日期：2026-10-31
- 状态：`proposed`
- 决策者：Develata（待批准）。沿用 ADR 0010 已定：两个 provider、问题按板块配置、shadow 走独立 `decision-run`、
  整个功能可移除
- 前置：[ADR 0010](./0010-typed-decision-capability.md)（Phase A 已合入 main `e0ffdd0`，两家真机探针通过）

## Context

Phase A 只交付了能力层：`crates/decision` 能对一篇文章发一次请求并返回校验后的类型化结果，但没有任何命令调用它。
Phase C 要用真实数据评估这些判断（与人工标注、与生成式 AI 的 `keep_decision` 对比），前提是先有一批按固定策略、
可追溯地跑出来的判断。Phase B 就是这个"影子运行"：只记录，不影响任何现有流程。

ADR 0010 §7 已给出的约束：

- 独立 `decision-run` 子命令，自有表，自有 claim / lease、有界并发、超时、重试上限与预算，双方言迁移；
- 只读文章，不写 `article_ai_results` / `articles.state`，不覆盖 `ai_raw_response`；
- 关闭时不建立任何连接；
- 表须能经新增迁移删除，并在本 ADR 给出删除步骤。

项目已有约束：

- 宪法 §3.2：新能力必须明确属于哪一层，禁止跨层混写；§3.5：新增平级模块，不侵入主干；
- ADR 0002：跨进程任务用数据库行级 claim + lease（`state`、`lease_owner`、`lease_expires_at`、`attempt_count`）；
- ADR 0005：`StoragePool` 枚举，每个 repo 方法按方言分派 SQL；
- non-goals §1.2：不自建 worker pool / 队列；并行靠多实例各自 claim；
- plan/00 §5 不变量 7：所有外部输入能力上可回放，由留档策略控制是否捕获；违反须审批。

现有 `ai-run` 的做法（本 ADR 的参照，均已对照源码核实）：

- task_gen 只看 `articles.state = 'persisted'`，并在同一事务把文章推进到 `ai_pending`
  （`crates/storage/src/repo/article_ai_result_impl.rs`）；
- claim 是单条 `UPDATE … WHERE id IN (SELECT … ORDER BY id LIMIT n)`，PostgreSQL 加 `FOR UPDATE SKIP LOCKED`；
  板块经 `articles → feed_entries → feed_sources.category_key` 三表 join 得到，`articles` 没有板块列
  （`article_ai_result_sql.rs`）；
- `attempt_count` 在 claim 时自增；retryable 释放用 `CASE WHEN attempt_count >= max THEN 终态 ELSE 'pending'`；
  每次释放都带 `WHERE id = ? AND lease_owner = ?`；
- 运行开始时 reclaim 过期 lease、把预算耗尽的 pending 行终态化；
- 一次 claim 一整批，再按 `[http].concurrent_fetches` 大小的 `JoinSet` 窗口执行；
  某批出现 retryable 失败后不再 claim 下一批，留给下次运行（`flows/ai_run/mod.rs` 的 `retryable_deferred`）；
- 没有 token / 费用预算，只有 `batch_size × max_batches`；没有进程内退避；
- doctor 的健康检查与 deep_scan 不变量把表名写死（`runtime/src/doctor/deep_scan.rs`）。

## Decision

### 1. 分层位置与可移除性（骨架决策）

候选：

- (a) 一个新 crate 同时放命令、flow 与 SQL：删除最简单，但把流程协调层与能力执行层写在一起，违反宪法 §3.2。**不采用。**
- (b) 按层各放专用文件，与现有流水线同构：**采用。**

| 层 | 位置 | 内容 |
|---|---|---|
| 指令接口层 | `crates/cli/src/commands/decision_run.rs` | 参数、装配、摘要输出 |
| 流程协调层 | `crates/runtime/src/flows/decision_run/` | `DecisionRunFlow` 与它自己的依赖 struct `DecisionRunDeps`（放在模块内，不进 `context.rs`） |
| 能力执行层 | `crates/storage/src/repo/decision_result{,_sql,_impl}.rs` | 表的全部 SQL 与 `DecisionResultState` |
| 能力执行层 | `crates/decision`（已有） | 客户端；本阶段只做两处小扩展（§6） |
| 迁移 | `migrations/{sqlite,postgres}/0006_decision_results.{up,down}.sql` | 建表与索引 |

- 新增依赖边：`runtime → decision`（模块图与 `modules.lisp` 同步）。storage 不依赖 decision：答案以 JSON 文本入库，
  序列化在 runtime 完成。
- 现有 flow、表、状态机与 `run` 命令都不改。
- **可移除性比 Phase A 弱**：Phase A 删一个 crate 加两处入口；Phase B 的逻辑全部在专用文件里，但要在几个共享文件里
  删登记行（`mod` / re-export / 枚举变体 / 分派 / 装配函数）。完整清单见 §10。

### 2. 状态机放在 storage，不进 domain

- `DecisionResultState`：`pending` → `running` → `succeeded` | `failed`；`running` → `pending`（retryable、退还、
  过期回收）；`pending` 且预算耗尽 → `failed`（扫描终态化）。
- 定义在 `crates/storage/src/repo/decision_result.rs`，不放 `crates/domain/src/state.rs`。
  - 理由：domain 是核心本体对象层（宪法 §3.1：订阅源、条目、正文、AI 结果、快照、产物）；typed-decision 是可整体移除
    的辅助实验对象，只被 storage 与这一个 flow 使用。放进 domain 会让移除再多一处，并让对象层出现实验性概念。
  - 代价：偏离 ADR 0002 "状态机集中在 domain/state.rs" 的惯例。plan/08 增加一节登记这个状态机并注明归属，避免漂移。

### 3. 表结构 `decision_results`

一行 = 一篇文章 × 一个策略版本 × 一个执行身份。

| 列 | 说明 |
|---|---|
| `id` | 主键（SQLite `INTEGER PRIMARY KEY`，PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`） |
| `article_id` | `NOT NULL`，FK → `articles(id)`（与 `article_ai_results` 相同，无 ON DELETE；当前没有代码删除文章） |
| `category_key` | 生成任务时由三表 join 写入，claim 不再 join |
| `policy_version` | 64 位小写 hex（ADR 0010 §6），含问题与 `max_state_chars` |
| `execution_key` | 执行身份，见下 |
| `provider` / `requested_model` / `laya_max_len` | 执行参数原值（`laya_max_len` 对 Jev 为 NULL） |
| `state` | §2 的状态 |
| `answers_json` | 成功时的归一化答案（§5） |
| `reported_model` / `routing_model` / `endpoint_origin` | 部署标识：provider 回报的模型与检查点、`base_url` 的 origin（仅 scheme + host + port） |
| `state_sha256` | 实际发送的 `state` JSON 的 SHA-256，用于事后确认判断的是哪段文本 |
| `body_chars_sent` / `body_truncated` | 本地按 `max_state_chars` 截断后的字符数，以及是否发生截断 |
| `provider_truncated` / `state_tokens_dropped` | Laya 的 `usage.truncated` / `state_tokens_dropped`；Jev 为 NULL |
| `input_tokens` / `latency_ms` | 用量与耗时 |
| `raw_response` | 留档的原始 2xx 响应体（§5），默认只在校验失败时写 |
| `lease_owner` / `lease_expires_at` / `attempt_count` | ADR 0002 的 lease 三列 |
| `last_error_kind` / `last_error` | `DecisionError` 的 `error_kind()` 与固定文本消息（不含 provider 内容） |
| `started_at` / `completed_at` / `created_at` / `updated_at` | 时间戳；SQLite 为 TEXT、PostgreSQL 为 TIMESTAMPTZ，均由应用绑定 UTC 值 |

- 约束：`UNIQUE (article_id, policy_version, execution_key)`；`CHECK (state IN (…))`；`CHECK (laya_max_len IS NULL OR provider = 'laya')`。
- 索引：`(state, lease_expires_at)`、`(category_key, state)`、`(article_id)`。
- **`execution_key`** 精确定义：
  - Jev：`jev:{model}`，如 `jev:jev-1.13.0`；
  - Laya：`laya:{model}:{laya_max_len}`，如 `laya:multilingual:2048`。
  - 不含 `base_url`、超时与并发：换部署地址或调参数不会让已判断的文章重跑；部署标识逐行记录，Phase C 可按它分组。
  - 换 provider、换模型、改 `laya_max_len` 或改问题（`policy_version` 变）都会对窗口内文章重新判断，旧行保留，便于对比。

### 4. 候选与任务生成

- 每个启用了问题的板块依次执行；问题为空的板块跳过。
- 候选：属于该板块、`created_at` 在最近 `window_hours` 内、`state <> 'retired'`、且没有同
  `(policy_version, execution_key)` 行的文章：

  ```sql
  SELECT a.id FROM articles a
  JOIN feed_entries fe ON fe.id = a.origin_feed_entry_id
  JOIN feed_sources fs ON fs.id = fe.source_id
  WHERE fs.category_key = $1 AND a.state <> 'retired' AND a.id > $2
    AND <created_at >= $3>          -- SQLite 侧按 R3 的 UTC 文本比较约定
    AND NOT EXISTS (SELECT 1 FROM decision_results d
                    WHERE d.article_id = a.id AND d.policy_version = $4 AND d.execution_key = $5)
  ORDER BY a.id ASC LIMIT $6
  ```

- 生成：按 keyset 分页插入 `pending` 行（`ON CONFLICT DO NOTHING`），本次运行最多生成到剩余请求预算为止。
  已存在的 pending 行（上次留下的 retryable）照常可被 claim，不受窗口限制。
- 不看、不改 `articles.state`：判断与文章是否已过 AI、是否已发布无关。
- 窗口的作用是首次启用时不把历史文章整批发给付费 API；需要补跑时用 `--window-hours` 显式放宽。

### 5. 结果与原始响应（不变量 7）

- `answers_json`：`{"schema":1,"answers":[…]}`，按问题顺序；每项带 `id`、`type`，以及：
  - noul：`p_yes`、`top_probability`（Laya 才有）；
  - choice：`label`、`probabilities`（label → p 的对象）、`spread_confidence {kind, value}`、`top_probability`；
  - score：`expected`、`probabilities`（下标即档位）、`spread_confidence`、`top_probability`。
  - 自描述：不依赖当时的配置即可读懂；`schema` 变化时只追加新版本。
- 原始响应留档用本表的 `raw_response` 列，不用 `raw_artifacts`：
  - `ArtifactKind` 是 domain 枚举，新增种类会改 domain；`raw_artifacts` 的 TTL 清理与 FK 置空也是为核心对象设计的。
    放在本表，删表即删干净。
  - 代价：仓库里出现第二条原始载荷存储路径；Phase B 不为它做 TTL 清理（见下方体量）。
- 策略 `[decision].raw_response`：`on_failure`（缺省）| `always` | `never`。
  - `on_failure`：只在响应为 2xx 但未通过校验（`InvalidResponse`）时保存——这正是需要事后排查契约漂移的情况；
    成功时归一化答案就是该外部输入经校验后的全部有效内容。
  - `always`：每次 2xx 都保存，供完全回放（每行约 1–3 KB）。
  - `never`：不保存。
  - 非 2xx 的错误体一律不保存、不回显（与 ADR 0010 §5 一致）；响应体含 API key 时不保存并记一条 warn 事件。
- 这样不变量 7 的"能力上可回放、由策略控制是否捕获"成立，不需要另行审批豁免。

### 6. 对 decision crate 的两处扩展

- 归一化结果类型增加 `Serialize`，并由 §5 的固定 JSON 形状测试锁定。
- 客户端在结果之外交出 2xx 响应体：`DecisionClient` 改为返回 `Exchange { result, raw_body: Option<Vec<u8>> }`。
  `raw_body` 只在 status 为 2xx 时为 `Some`；`Exchange` 的 Debug 不打印字节。Phase A 的其余契约不变。

### 7. claim、lease、并发与预算

新增 `[decision]` 字段（全部在 decision crate 解析与校验，不进 config crate 的类型）：

| 字段 | 缺省 | 范围 | 作用 |
|---|---|---|---|
| `concurrency` | 2 | 1..=8 | 一批内同时在途的请求数 |
| `lease_seconds` | 300 | 30..=3600 | 一批的 lease 时长 |
| `max_attempts` | 3 | 1..=10 | 每行的尝试上限 |
| `max_requests_per_run` | 100 | 1..=10000 | 单次运行发出的请求上限 |
| `window_hours` | 48 | 1..=8760 | 候选窗口 |
| `raw_response` | `on_failure` | 见 §5 | 原始响应留档 |

CLI：`decision-run [--category KEY] [--batch-size N(默认 20，1..=500)] [--max-requests N] [--window-hours N]`。

- **claim**：与 ai-run 同形——单条 `UPDATE … WHERE id IN (SELECT … WHERE state = 'pending' AND
  (lease_expires_at IS NULL OR lease_expires_at < now) AND attempt_count < max AND category_key = ? ORDER BY id LIMIT n)`，
  PostgreSQL 加 `FOR UPDATE SKIP LOCKED`；`attempt_count` 在 claim 时自增；所有释放都带 `WHERE id = ? AND lease_owner = ?`。
- **维护**：运行开始时 reclaim 过期 lease、把预算耗尽的 pending 行终态化为 `failed`（kind `retry_budget_exhausted`）。
- **并发**：一批 claim 后按 `concurrency` 大小的 `JoinSet` 窗口执行，与 ai-run / extract 相同。这是"单实例内对一批已领取任务
  的在途请求上限"，不是 worker pool 或队列，不违反 non-goals §1.2；跨实例并行仍靠各自 claim。
  用独立的 `concurrency` 而不是 `[http].concurrent_fetches`：自部署 Laya 的吞吐与通用抓取无关。
- **lease 预算**：运行前检查 `ceil(batch_size / concurrency) × request_timeout_seconds ≤ lease_seconds`，
  不满足即以配置错误退出（同 ai-run 的 lease 预算检查）。
- **请求预算**：每次 claim 的数量取 `min(batch_size, 剩余预算)`，每行恰好一个请求（没有 fallback 链），
  因此单次运行发出的请求数 ≤ `max_requests_per_run`，这是一条安全性质。
  - 以缺省值估算最坏用量：100 次 × 每次最多约 6000 字符正文（`max_state_chars`），Jev 按输入 token 计费，
    单次运行在百万 token 以内；实际以账单为准。
- 没有进程内 sleep 或退避：重试发生在下一次运行，间隔由外部调度决定。`Retry-After` 只记入事件。

### 8. 失败分类与重试

| 类别 | `DecisionError` | 处理 |
|---|---|---|
| 成功 | — | `succeeded`，写答案与元数据 |
| 单篇、可重试 | `Timeout`、`RequestTimeout`、`Unavailable`、`Server` | 回 `pending`，计一次尝试（到上限即 `failed`）；本批结束后不再 claim 下一批 |
| 单篇、永久 | `InvalidResponse`、`PayloadTooLarge`、`ResponseTooLarge`、`Rejected` 且 code 为 `max_tokens_exceeded` | `failed` |
| 全局、与文章无关 | `Unauthorized`、`Connection`、`RateLimited`、`InvalidConfig`、`InvalidRequest` | **中止本次运行**：不再启动新请求、不再 claim；触发行与本批所有未启动的行回 `pending` 并**退还**尝试次数 |
| 全局、疑似配置 | 其它 `Rejected`、`UnsupportedEncoding`、`HttpStatus`（含 3xx、404） | 中止本次运行；未启动的行退还，**触发行计一次尝试** |

- 退还：释放 SQL 写 `attempt_count = attempt_count - 1`（claim 时已加一），同样受 `lease_owner` 约束。
- 已在途的请求照常完成并释放。
- "疑似配置"一类让触发行计次，是为了避免某篇文章确实触发 400 时每次运行都卡在它身上：它最多卡 `max_attempts`
  次运行，之后终态化，后面的文章继续。凭据或网络问题不会消耗任何文章的尝试次数。
- Laya 的 503 可能由输入确定性触发（ADR 0010 §5），因此归入"单篇、可重试"，由尝试上限兜底。
- 退出码：`Unauthorized` / `InvalidConfig` / `InvalidRequest` → 78；`Connection` 与"疑似配置"类 → 1；
  `RateLimited` → 0，摘要标记 `rate_limited`；单篇失败不影响退出码（同 ai-run）。
- 任何失败都只表示"没有判断"，不得推断为文章不重要（ADR 0010 §5）。

### 9. 命令、可观测性与边界

- `decision-run` 是独立子命令，**不加入 `run`**，部署方另配一条调度。
- `[decision]` 缺失或 `enabled = false`：在打开存储与构造客户端之前以退出码 78 结束，不建立任何连接。
  启用时先解析凭据、校验问题与 lease 预算，再打开存储（与 ai-run 相同，写命令会自动执行迁移）。
- 不支持 `--dry-run`（同 ai-run）。
- run_events：stage `decision_run`；事件 `run_started`、`run_completed`、`decision_completed`、`decision_failed`
  （带 `error_kind`、类别、`retryable`）、`decision_run_aborted`、`leases_reclaimed`、`retry_budget_swept`；
  target 为 `("decision_result", id)`。事件里不放文章内容与答案。
- 摘要（文本与 JSON 两种输出）：各板块的 generated / claimed / succeeded / failed / retried / refunded、请求数、
  input_tokens 合计、`aborted`（kind）、`budget_exhausted`、`rate_limited`、耗时。
- **doctor 不纳入**：健康检查与 deep_scan 不认识 `decision_results`。加进去会让 doctor 依赖这个可移除的功能。
  该表的 lease 回收与预算终态化由 `decision-run` 自己在运行开始时完成，状态通过摘要与 run_events 可见。
  这是有意保留的观测缺口，Phase C 若决定让判断参与流程，再连同 doctor 一起设计。

### 10. 移除步骤

1. 新增前向迁移 `0007_drop_decision_results`（两方言 up / down，`DROP TABLE`），并在迁移 pin 测试中登记。
   `0006` 与 `0007` 的文件必须永久保留：已执行过的数据库记录了它们的校验和。
2. 删 `crates/cli/src/commands/decision_run.rs`；在 `args.rs` 删 `Command::DecisionRun` 与参数 struct 及其在
   `name()` / `accepts_dry_run()` 中的分支；删 `commands/mod.rs` 的分派行与 `context_factory.rs` 的装配函数。
3. 删 `crates/runtime/src/flows/decision_run/` 与其 `mod` 行；删 runtime 对 decision 的依赖。
4. 删 `crates/storage/src/repo/decision_result*.rs` 与 `repo/mod.rs`、`lib.rs` 中的登记行。
5. 再按 plan/18 §1 删除 Phase A。
6. 文档：本 ADR 改为 `deprecated`；删 plan/18 的 Phase B 章节、plan/08 的状态机登记、cli-reference 与验收用例、地图条目。

### 11. 测试

- storage（SQLite 进程内；PostgreSQL 走现有 postgres lane）：候选的窗口 / 板块 / 反连接、重复生成不产生重复行、
  并行 claim 不相交、错 owner 释放无效、过期回收、预算终态化、退还与计次两种释放。
- flow（假 `DecisionClient`）：§8 每个类别的状态变化与退出码、请求预算上限、批间 retryable 停止、中止时未启动行的退还、
  `raw_response` 三种策略、事件内容不含正文与答案。
- CLI：参数、关闭时退出码 78 且不打开存储、lease 预算检查、摘要 JSON 形状。
- decision crate：`answers_json` 固定形状、`Exchange` 只在 2xx 时带原始体且 Debug 不含字节。
- 迁移：pin 与双方言配对测试。
- 手工验收：对临时 SQLite 库与合成文章，用用户的 Laya 实例跑一次 `decision-run`，只用合成数据。

## Consequences

### 正面后果

- 有了可追溯的判断数据：每条结果都能对回策略版本、执行身份、部署标识与实际发送的文本，Phase C 可以直接评估。
- 主流程、现有表与状态机零改动；关闭时零连接。
- 请求数有硬上限，凭据或网络故障不消耗文章的尝试次数。

### 负面后果 / 代价

- 可移除性弱于 Phase A：除专用文件外，还需在约 8 处共享文件删登记行，并留下两对不可删的迁移文件。
