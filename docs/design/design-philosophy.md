# RSS-AI-News 核心设计哲学

## 1. 设计目标

本项目不是“一个抓 RSS 的脚本集合”，而是一个：

- 长期运行
- 可恢复
- 可审计
- 可回放
- 可发布
- 可演化

的内容处理系统。

它的终局形态必须在首版骨架阶段就被约束住，而不是等功能做多以后再拆。

## 2. 基本哲学

### 2.1 骨架先于实现

首版功能永远不能定义系统本体。  
首版只决定“先做什么”，不决定“系统是什么”。

### 2.2 本体对象优先

系统的骨架围绕以下对象建立：

- `FeedSource`
- `FeedEntry`
- `Article`
- `ArticleAiResult`
- `PublishSnapshot`
- `PublishedArtifact`

所有模块、状态机、数据库和 CLI 命令都必须围绕这些对象展开。

### 2.3 阶段驱动，而非脚本驱动

系统不是一条“从头跑到尾”的脚本，而是若干可恢复、可重试、可审计的阶段：

1. 发现 feed 条目
2. 早去重
3. 抓正文
4. 提正文
5. 存文章
6. 跑 AI
7. 冻结发布快照
8. 渲染与发布

一切运行时行为都应表达成阶段状态变化。

### 2.4 快照优先

对会被展示、发布、审计的结果，必须优先冻结快照，再做后续处理。

典型例子：

- 发布不是“实时查库然后直接渲染”
- 而是“先冻结 `PublishSnapshot`，再渲染 Markdown，再推送 GitHub”

### 2.5 回放优先

外部世界不可靠，所以系统必须能在脱离外网的条件下重放关键输入。

必须至少能重放：

- feed payload
- HTML payload
- AI raw response

这决定了系统未来排错方式，也决定了哪些对象必须被允许留档。

### 2.6 租约优先

只要某任务可能被多个 worker 消费，就必须从第一版开始按 claim + lease 模型设计。

不能依赖：

- 单进程假设
- “反正现在只有一个 worker”
- 简单 `pending/running` 状态

### 2.7 单一真相源

核心对象的最终依据必须唯一：

- source 真相源在数据库
- article 真相源在数据库
- publish 真相源在发布快照表
- 配置真相源在结构化配置对象及其版本

内存对象永远只能是投影，不能是事实本身。

## 3. 架构表达方式

### 3.1 四层架构 + 对象层

系统以以下结构组织：

1. 交互壳层
2. 指令接口层
3. 流程协调层
4. 能力执行层
5. 对象层

#### 交互壳层

负责：

- CLI 输入
- 输出呈现
- 参数转译

#### 指令接口层

负责：

- `action -> intent`
- `intent -> state delta`
- `state delta -> capability requests`

#### 流程协调层

负责：

- 编排 use-case
- 协调前后依赖
- 推进状态
- 处理中止与补偿

#### 能力执行层

负责：

- 网络通信
- 数据存储
- HTML 提取
- AI 调用
- 文件系统与 GitHub 发布

#### 对象层

定义最小操作对象，例如：

- `sql::feed_source`
- `sql::feed_entry`
- `sql::article`
- `data::html`
- `data::xml`
- `data::markdown`
- `artifact::raw_payload`

## 4. 根基兼容性哲学

### 4.1 兼容根基，不重复发明根基

对于长期存在、底层基础、被大规模接受并稳定运转的外部生态，应优先兼容，而不是重造。

对本项目而言，必须兼容的根基主要包括：

- CA 证书体系
- TLS / HTTP 标准行为
- 时区数据库
- Git / GitHub API 生态
- Rust 关键依赖生态

### 4.2 适配层隔离变化

所有可能演化的外部协议都必须通过适配层进入系统，例如：

- `HttpClient`
- `AiClient`
- `PublisherTarget`
- `TimezoneProvider`

这样未来变化只改 adapter，而不拖动 domain 和 runtime 主骨架。

## 5. 可维护性与可诊断性哲学

### 5.1 失败先于成功

任何核心流程都必须先定义失败路径，再定义成功路径。

### 5.2 解释性优先

系统必须能解释：

- 为什么这条被去重
- 为什么这条正文提取失败
- 为什么这条被 AI 过滤
- 为什么它没进入日报

否则系统会变成不可维护的黑箱。

### 5.3 版本责任前置

以下对象都必须带版本语义：

- 配置 schema
- 正文提取规则
- Prompt
- AI 输出协议
- 发布渲染版本
- 数据库 migration

### 5.4 退出路径与生命周期完整

系统不仅定义对象如何进入，也必须定义对象如何退出：

- source 停用
- artifact 过期
- snapshot 归档
- 本地报告迁移 / 删除

## 6. 性能、内存与外存哲学

### 6.1 性能服务于骨架，而不是主导骨架

性能优化必须在不破坏以下对象的前提下进行：

- 骨架稳定
- 根基兼容性
- 可诊断性

### 6.2 内存优化靠数据流边界，而不是语言幻想

真正的低内存依赖：

- 早去重
- 有界队列
- payload 生命周期控制
- 分阶段落库
- 不全量缓存

### 6.3 外存优化必须服从回放与审计需求

raw artifact 与 publish snapshot 的保留策略必须可配置，而不是直接删掉或全部永存。

## 7. 终局判断

这个项目的终局不是“写成 Rust 就结束”，而是建立一个：

- 骨架稳定
- 规则版本化
- 输入可回放
- 发布可复现
- 故障可追踪
- 适配层可替换

的系统。

如果未来的实现偏离这个方向，即使局部功能做出来了，也不算忠于本项目的设计哲学。
