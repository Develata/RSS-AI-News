# 存储多方言适配设计

## 1. 定位

本文档是 storage crate **方言适配层**的实现级契约，承接 [storage-schema](./storage-schema.md) 的 schema 契约，补完 SQLite 与 PostgreSQL 双 backend 实现的工程约束。

它回答以下问题：

- backend 抽象边界放在哪一层
- 哪些 SQL 形态跨方言**等价**、哪些**需要差异化**
- lease / 事务原子性在两个 backend 上如何**等价兑现**
- PG schema 如何从现有 SQLite migration 翻译而来
- 集成测试如何在两个 backend 上**同等覆盖**

### 1.1 起因

F15 batch 后 codex 二审发现：`README.md` 与 `crates/config/src/env.rs:18-31` 都声明 `DATABASE_URL` 可切换 PostgreSQL，但 `crates/storage/`、`crates/cli/src/context_factory.rs` 全部硬绑 `SqlitePool` —— 契约与实现存在裂缝。本设计的目的是**关掉这条裂缝**，让 README 承诺成为实现现实。

### 1.2 范围

In-scope：
- storage crate 内部 backend 抽象
- migrations 双目录布局
- repo trait 内部分发模式
- 集成测试参数化
- CI 双轨

Out-of-scope：
- **SQLite → PostgreSQL 数据迁移**（PG 视为新部署；老用户继续 SQLite 路径）
- **JSONB 等 PG 高级类型优化**（初期保留 TEXT 兼容 SQLite，留 W11+ 单独评估）
- **配置版本化协同**（codex P0-1 + 私有 memory `project-bootstrap-rule-active-seam`：留给独立的 `docs/design/config-versioning.md`，W10 之后；多方言落地后自动得到 PG 支持）

## 2. 总原则

### 2.1 方言为实现细节

所有 backend 差异在 storage crate 内消化。`runtime` / `cli` 层不感知当前是 SQLite 还是 PostgreSQL；它们持有的 trait object（`dyn FeedSourceRepository` 等）行为契约跨方言一致。

### 2.2 类型枚举式 backend，不用 sqlx Any driver

```rust
pub enum StoragePool {
    Sqlite(sqlx::SqlitePool),
    Postgres(sqlx::PgPool),
}
```

repo 内部 `match` 分发。**拒绝 sqlx `Any` driver** 的理由：
- `Any` 类型 erasure 后 bind 校验是运行期的，错误信息差
- `query!` 编译期校验宏只能绑单一后端，不能复用
- enum 分裂虽多写一倍 backend 函数体，但 SQL 字符串可共享（见 §6.2），主要重复在 sqlx 类型签名而非业务逻辑

### 2.3 lease / 事务跨方言语义等价

SQLite WAL 整库写锁 与 PG row-level lock 在表现上不同，但在 lease 表（`reindex_jobs` / `feed_entries` / `article_ai_results` / `publish_records`）上必须产生**相同可观察行为**：

> `UPDATE T SET lease_owner=?, lease_expires_at=? WHERE id=? AND state='running' AND lease_owner=? RETURNING ...` 的 `rows_affected` 在两个 backend 上对**同一并发场景**给出相同的真/假判定。

PG 上 UPDATE 语句自动持有被命中行的 row-level lock 直到事务结束，与 SQLite WAL 的事务级写锁在 "Lease Guard + 同事务后续写入" 模式（[F15-fix7](../../../docs/design/state-machine.md)）下提供等价保证。**不引入 advisory_lock / SELECT FOR UPDATE** —— 那会把 lease 状态从表里渗到连接级状态，破坏 "lease 单一真相源" 的设计原则。

### 2.4 schema 编号统一空间

SQLite 和 PostgreSQL 共用一套 `NNNN_short_name` migration 编号。同一编号下两套 schema 语义对等，由 CI 校验。**不**让两套 schema 各自演化编号。

### 2.5 应用层是 id 唯一分配者，禁止硬编码 id INSERT

任何写入 `rule_versions` 等带自增主键表的代码路径**禁止显式带 id**（`INSERT ... (id, ...) VALUES (1, ...)` 即被禁）。这是 PG `GENERATED BY DEFAULT AS IDENTITY` 的硬约束：

- 显式插入 id **不推进 sequence**，后续隐式 INSERT 会再次生成已存在 id 触发主键冲突
- 即便改成 `ON CONFLICT(id) DO NOTHING`，也会在 id=1 已被其它 `kind` 占用时**静默跳过**，语义错误

现有违规点：[`crates/cli/src/context_factory.rs:191-200` `ensure_default_rule_version`](../../crates/cli/src/context_factory.rs)。**P1 阶段必须改写**为 `active_rule_or_register("config", "cli-default", config_sha256, ...)`（已有 F15-fix6 的 `active_rule_or_register` 路径），自然分配 id 并维持 active 单根不变量。

## 3. 风险决议表

| 风险 | 决议 | 拒绝的备选 | 拒绝理由 |
|---|---|---|---|
| backend 抽象方式 | enum 分裂 (`StoragePool::{Sqlite, Postgres}`) | sqlx `Any` driver | 类型 erasure、编译期校验失效 |
| lease 表并发竞争 | `UPDATE...WHERE state='running' AND lease_owner=? RETURNING` + `rows_affected` 谓词 | `pg_advisory_lock` / `SELECT FOR UPDATE` | 跨连接状态，违反 "lease 单一真相源" |
| 时间存储 | SQLite TEXT(RFC3339) / PG TIMESTAMPTZ；Rust 侧统一 `OffsetDateTime` | 两边都 TEXT | 浪费 PG 强类型；与 [storage-schema §2.3](./storage-schema.md) 契约一致 |
| 占位符 `?` vs `$N` | 全仓改 `$N`（SQLite 也支持） | 运行期模板替换 / 双 SQL 字符串 | 模板器脆弱；双 SQL 维护成本翻倍 |
| `INSERT OR IGNORE` | 改 `INSERT ... ON CONFLICT DO NOTHING` | 保留 SQLite-only 写法 + PG 分支 | ON CONFLICT 自 SQLite 3.24 标准化，两边可统一 |
| `keep_decision` 数据类型 | 保留 `INTEGER` 0/1；领域层 `bool`，storage 边界 bind/decode `i32` | PG 升 `BOOLEAN` | DB 列跨方言一致（都 INTEGER）；领域层 bool 与 storage 边界 i32 分离，保证 `0`/`1` 字面量在 PG 上是 INT4 |
| SQLite → PG 数据迁移 | **不做** | 写一次性迁移工具 | 投入产出比低；PG 视为新部署 |
| schema 编号 | 统一一套 NNNN | 各自编号 | 防止版本漂移；CI 易校验 |
| `rule_versions` bootstrap | 走 `active_rule_or_register("config", ...)` 自然分配 id | `INSERT (id=1, ...) ON CONFLICT DO NOTHING` | PG IDENTITY 不推进 sequence；id=1 被占用时静默跳过语义错误 |
| `driver` 与 `DATABASE_URL` 优先级 | URL scheme 决定 backend，`driver` 字段必须与 URL scheme 一致；不一致即配置错误（当前 `DatabaseDriver` enum 只有 `sqlite` / `postgres`，无 `Auto`） | 静默使用其中一个 / 引入 `Auto` 模糊态 | 防止"配置说 sqlite、URL 是 postgres"的隐式漂移；`Auto` 会让 driver 字段失去校验意义 |

## 4. 类型映射

### 4.1 通用语义映射

| 语义 | SQLite | PostgreSQL | Rust |
|---|---|---|---|
| 主键 64 位自增 | `INTEGER PRIMARY KEY` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `i64` |
| FK / 大计数 | `INTEGER` | `BIGINT` | `i64` |
| 评分（0-100） | `INTEGER` | `INTEGER` (INT4) | `i32`（`Score0To100` 内部） |
| Token / 延迟 | `INTEGER` | `BIGINT` | `i64`（详见 §4.2 行：读模型 `Option<i64>`） |
| 0/1 决策 | `INTEGER` (`CHECK ... IN (0,1)`) | `INTEGER` (`CHECK ... IN (0,1)`) | 领域层 `bool`；storage 边界 bind/decode `i32`（详见 §4.2 `keep_decision` 行） |
| 文本 | `TEXT` | `TEXT` | `String` |
| 字节串 | `BLOB` | `BYTEA` | `Vec<u8>` |
| 时间戳（UTC） | `TEXT`（RFC3339 `YYYY-MM-DDTHH:MM:SS.fffZ`） | `TIMESTAMPTZ` | `time::OffsetDateTime` |
| JSON 载荷 | `TEXT`（序列化后） | `TEXT`（初期；JSONB 留 W11+） | `String` |

### 4.2 列级整数宽度映射（PG 必须按 Rust 字段类型选 INT4 / INT8）

SQLite `INTEGER` 是动态类型 `INTEGER`-storage-class，对 sqlx Encode/Decode 兼容 `i32` / `i64`；PG **强类型 INT4 vs INT8**，bind / decode 必须与 Rust 字段类型对齐，否则 `decode` 在 P3 翻车。

**当前代码存在"读模型 / 写入 DTO"类型不一致**，必须先在 P1 内消除歧义（见下表 "Action" 列）：

| 表.列 | 读模型（domain）类型 | 写入 DTO 类型 | PG 列类型 | P1 Action |
|---|---|---|---|---|
| `*.id` / `*.source_id` / `*.article_id` / `*.feed_entry_id` / `*.rule_version_id` / `*.run_id` / `*.byte_size` | `i64` | `i64` | `BIGINT` | ✅ 一致，无改动 |
| `article_ai_results.importance_score` ／ `publish_items.importance_score` ／ `publish_items.frozen_score` | `Option<Score0To100>`（内部 i32） | `Option<i32>`（`AiSuccessOutcome`） | `INTEGER`（INT4） | ✅ 一致，与 [`Score0To100::Type<Postgres>`](../../crates/domain/src/score.rs:105) 已声明的 INT4 对齐 |
| `article_ai_results.tokens_in` ／ `tokens_out` ／ `latency_ms` | `Option<i64>`（`ArticleAiResult`） | `Option<i32>`（`AiSuccessOutcome`） | **`BIGINT`**（按读模型选） | ⚠️ **将 `AiSuccessOutcome` 三字段升 `Option<i64>`**（轻量重构 < 10 行），PG 列锁定 `BIGINT`；不收窄读模型，避免 token 计数未来超出 i32 范围 |
| `article_ai_results.keep_decision` | `Option<bool>` | `Option<bool>` | `INTEGER`（CHECK IN (0,1)） | ⚠️ storage 层在 bind / decode 边界做 `bool ↔ i32` 转换，PG bind 用 `i32`（**不是 `i64`**——PG `0`/`1` 字面量是 INT4），CHECK 谓词跨方言兼容 |
| `*.attempt` ／ `*.attempt_count` ／ `*.retry_count` ／ `*.max_retries` | `i64`（部分字段） / `i32`（部分字段） | 按字段 | 按字段对齐：`i64` → `BIGINT`，`i32` → `INTEGER` | P2 schema 翻译时逐字段对照 row struct，不二选一 |
| `*.lease_owner_token` ／ `*.version` 等 | `i64` | `i64` | `BIGINT` | ✅ 一致 |

判定原则：

- **单一真相源 = 读模型（domain crate）字段类型**。写入 DTO 与 PG 列类型都必须**追随读模型**，不允许逆向把读模型收窄迁就 DTO
- 任何 DTO 与读模型类型不一致**视为 P1 必修缺陷**——见上表 ⚠️ 行
- 实际逐列在 P2 schema 翻译时**对照读模型 row struct**落到 `migrations/postgres/0001`，不依赖 DTO
- 历史代码若已用 `i32` bind 写入（如 `AiSuccessOutcome`），升 `i64` 时同步检查所有调用点（`crates/ai/`、`crates/runtime/flows/ai_run.rs`），属 P1 子任务

### 4.3 重要约束

- 不依赖 DB 默认值 `DEFAULT CURRENT_TIMESTAMP` —— SQLite 输出 `YYYY-MM-DD HH:MM:SS`（无毫秒、无 `Z`），与 [storage-schema §2.3](./storage-schema.md) 字面规约不符。生产路径全部**应用层显式 bind** `OffsetDateTime::now_utc()`；DB 默认值仅作 migration 时回填的异常兜底
- `keep_decision` 等 0/1 整数列**不**升级为 PG `BOOLEAN`；领域层保持 `bool`，storage 边界 bind/decode 用 `i32`（PG `0`/`1` 字面量是 INT4）
- 整数宽度**不一致即 decode error**：写 PG schema 时按 §4.2 列级表对照 Rust 字段定夺

## 5. SQL 方言差异点清单

### 5.1 跨方言等价（无需差异化）

- `ON CONFLICT(col) DO UPDATE / DO NOTHING`（SQLite 3.24+ / PG 9.5+）
- `RETURNING`
- Partial unique index：`CREATE UNIQUE INDEX ... WHERE status='active'`
- 占位符 `$1, $2, ...`（SQLite 也支持）
- `FOREIGN KEY ... ON DELETE CASCADE / SET NULL`
- `CHECK (...)` 约束

### 5.2 跨方言差异（需要适配）

- 主键自增：`INTEGER PRIMARY KEY` (SQLite) vs `BIGINT GENERATED BY DEFAULT AS IDENTITY` (PG)
- 时间默认值：`DEFAULT CURRENT_TIMESTAMP` (SQLite) vs `DEFAULT NOW()` (PG)
- 字节类型：`BLOB` (SQLite) vs `BYTEA` (PG)
- `SELECT EXISTS(...)` 返回类型：SQLite decode 为 `i64`（0/1）；PG decode 为 `bool`。直接用 `query_scalar::<_, i64>` 在 PG 上类型不匹配。统一改写见 §5.3 第 3 行——SQL 写 `SELECT CASE WHEN EXISTS(...) THEN 1 ELSE 0 END`，**decode 用 `i32`**（PG 的 `1`/`0` 字面量推断为 INT4；SQLite INTEGER storage class decode 到 `i32` 同样合法）。**不要**写 `1::BIGINT`——SQLite 不支持 `::TYPE` 后缀 cast 语法
- 生产 SQL 内嵌时间函数：`CURRENT_TIMESTAMP` / `datetime('now')` / `datetime('now', '+10 minute')` 在 SQLite 是 TEXT 输出；PG 的 `NOW()` / `now() + interval '10 minutes'` 返回 `TIMESTAMPTZ`。这类内嵌时间表达式**不跨方言等价**，必须由应用层 bind `OffsetDateTime`
- 当前未使用，但 PG 不支持，需禁用：`AUTOINCREMENT` / `strftime` / `julianday` / `json_extract` / `PRAGMA` / `WITHOUT ROWID`

### 5.3 必须改写的已有代码

### 5.4 `driver` 与 `DATABASE_URL` 优先级（P0 决议）

[`AppConfig.database.driver`](../../crates/config/src/app.rs:27) 与 [`env.database_url`](../../crates/config/src/env.rs:18) 同时存在。`StoragePool::build` 阶段需先校验：

1. **URL scheme 决定 backend**：`postgres://` / `postgresql://` → `Postgres`；`sqlite://` 或裸路径 → `Sqlite`
2. **`driver` 字段必须与 URL scheme 一致**，否则走 [`ConfigError::ValidationFailed`](../../crates/config/src/error.rs:14) + `Diagnostic { field_path: "database.driver", message: "driver/DATABASE_URL scheme mismatch: ..." }`（fail-fast；复用现有 `DiagnosticReport` 通路，不新增 enum variant）
3. **`driver=postgres` 必须有显式 `DATABASE_URL`**：PG 没有 `sqlite_path` 那样的默认本地路径，缺失即同样走 `ValidationFailed` Diagnostic（`field_path: "env.database_url"`）
4. **`driver=sqlite` 时 `DATABASE_URL` 可空**：fallback 到 `database.sqlite_path`

CLI 启动期由 `cli::context_factory::build_run_context` 调一次 `validate_db_url_driver_consistency(cfg)` 验证。该函数返回 `Result<(), ConfigError>`，失败时直接构造 `DiagnosticReport` 包装成 `ValidationFailed`。

## 6. Rust 抽象层设计

### 6.1 Pool 枚举

```rust
// crates/storage/src/pool.rs
pub enum StoragePool {
    Sqlite(sqlx::SqlitePool),
    Postgres(sqlx::PgPool),
}

impl StoragePool {
    pub async fn build(
        url: &str,
        max_connections: u32,
        busy_timeout_ms: u32,
    ) -> Result<Self, StorageError> {
        if url.starts_with("postgres://") || url.starts_with("postgresql://") {
            Ok(Self::Postgres(build_pg_pool(url, max_connections).await?))
        } else {
            Ok(Self::Sqlite(
                build_sqlite_pool(url, max_connections, busy_timeout_ms).await?,
            ))
        }
    }
}
```

DATABASE_URL 路由由 `cli::context_factory::build_run_context` 调用 `StoragePool::build` 完成。env.rs 内孤立的 `database_url: Option<String>` 字段终于有了消费点。

**P2 阶段边界（重要）**：P2 期间 `StoragePool::build` 能构造 `PgPool` 并 `apply migration`，但 **repo 业务方法的 PG 分支均未实现**。为防止运行期掉进未实现 match arm，P2 必须在两层 fail-fast：

1. **`build_run_context` 启动期拦截**：若 `driver=postgres`，且当前 CLI 子命令 ≠ `cli migrate`（包括 `run` / `ingest` / `ai-run` / `publish` / `doctor`），直接返回 `StorageError::UnsupportedBackend("postgres repo path is P3+, current command only supports sqlite")`
2. **repo trait 内部分发 match arm**：所有 `match &self.pool { StoragePool::Postgres(_) => Err(StorageError::UnsupportedBackend(...)), ... }`，P2 阶段是显式 stub；P3 起逐 repo 替换为真实实现

P2 期间仅 `cli migrate` 子命令对 `driver=postgres` 放行，用于跑通 `migrations/postgres/0001` 的 apply 测试。

**P3-A 进度（W11-P3-A）**：`StoragePool::build` PG 分支已实装 [`build_pg_pool`]，`migrations/postgres/{0001,0002}.{up,down}.sql` 已落盘，`run_migrations(&StoragePool)` 按 backend 分发；`migration_pair_parity_tests` 在 CI 上保护编号配对；`migrations_postgres_apply_tests`（`#[ignore]`，需 `--include-ignored` + docker）已在本地 PG 16-alpine 容器上跑通幂等 apply。**repo 业务方法仍保持 P2 阶段的 [`StoragePool::require_sqlite`] stub** —— `git grep "postgres path is P3+"` 一次扫齐所有 stub 点，P3-C 起逐 repo 迁出。

### 6.2 Repo trait 内部分发

P2-B 后所有 repo struct 已从 `Sqlite*Repo` 重命名为 `*Repo`（如 `FeedSourceRepo`），内部持有 `StoragePool`，trait 方法 `match` 分发：

```rust
pub struct FeedSourceRepo { pool: StoragePool }

#[async_trait]
impl FeedSourceRepository for FeedSourceRepo {
    async fn upsert(&self, src: &FeedSource) -> Result<i64, StorageError> {
        match &self.pool {
            StoragePool::Sqlite(p) => self::sqlite::upsert(p, src).await,
            StoragePool::Postgres(p) => self::postgres::upsert(p, src).await,
        }
    }
    // ... 其他方法同模式
}

mod sqlite { /* SQLite 绑定具体实现 */ }
mod postgres { /* PG 绑定具体实现 */ }
```

**SQL 字符串可部分共享**：ON CONFLICT、`$N`、RETURNING、partial unique 都跨方言一致；纯文本 SQL 同一字符串两侧通用。**但**：

- sqlx 类型签名分叉**不可避免**——`Transaction<'_, Sqlite>` vs `Transaction<'_, Postgres>`、`SqlitePool` vs `PgPool`、Row 类型不同
- 内嵌时间函数（`CURRENT_TIMESTAMP` / `datetime('now')` vs `NOW()`）即使外形相似，**仍属两个方言**——参见 §5.3 P1 必改清单
- `SELECT EXISTS(...)` 返回类型不同——§5.3 已要求统一改 `CASE WHEN ... THEN 1 ELSE 0 END`
- `Score0To100` 等 domain 类型 `impl Type<DB>` 已经按 backend 分裂

施工预期：每个 repo 文件大致 1.3-1.5x 行数膨胀，主要在 sqlx helper 函数；SQL 字符串本体约 70-80% 可共享。

### 6.4 Transaction

`pool.begin()` 在两个 backend 上语义对齐：

- SQLite deferred tx 第一条 UPDATE 取整库写锁，跨 statement 持有到 commit
- PG 默认 READ COMMITTED + 命中行 row-level lock，跨 statement 持有到 commit

对 [F15-fix7](./state-machine.md) 的 lease guard 模式（lease UPDATE + feed_source 写入同事务）：

| 属性 | SQLite | PostgreSQL |
|---|---|---|
| 同事务内 UPDATE rows_affected | 真实视图 | 真实视图 |
| commit 前他事务可见性 | 否（整库写锁） | 否（row lock + READ COMMITTED） |
| lease guard rows_affected=0 + rollback | feed_sources 写入消失 | feed_sources 写入消失 |

**结论**：fix7 设计在 PG 上**不需要额外语义补丁**；但需要新增 §8.4 的并发竞争测试**实证**这一点。

**批量 claim 路径（多 worker 竞抢同一表）**：PG 分支正式契约必须用 `FOR UPDATE SKIP LOCKED`，例如：

```sql
-- PG: SELECT 候选 + 立即跳过被锁行
SELECT id FROM reindex_jobs
 WHERE state = 'pending'
 ORDER BY created_at
 LIMIT $1
 FOR UPDATE SKIP LOCKED
```

理由：

- 不加 `SKIP LOCKED` 时高并发 worker 会序列化排队等行锁，等价单 worker
- SQLite 不支持 `FOR UPDATE`，但 SQLite 没有"多 worker 真并发"语义（整库写锁），单 worker `SELECT ... LIMIT N` 自然不冲突
- 故 PG 分支必须显式 `FOR UPDATE SKIP LOCKED`，SQLite 分支保留原查询；不是"推荐"而是契约

### 6.6 错误分类（SQLSTATE）

当前 [`crates/storage/src/error.rs:71-108`](../../crates/storage/src/error.rs) 的 `classify_sqlite_error` / `is_unique_constraint` / `is_foreign_key_constraint` 只识别 SQLite 错误码（`2067` / `1555` unique、`787` FK）+ 字符串匹配。**P3 必须扩展为多方言分类器**：

```rust
// classify_db_error(error, table, key)
// SQLite 沿用现有 2067/1555/787 + message 兜底
// PG 走 SQLSTATE：
//   23505  unique_violation       → StorageError::Conflict
//   23503  foreign_key_violation  → StorageError::Integrity
//   23502  not_null_violation     → StorageError::Integrity（暴露字段名）
//   23514  check_violation        → StorageError::Integrity
//   40001  serialization_failure  → StorageError::Unavailable（可重试；标记 is_retryable=true）
//   40P01  deadlock_detected      → StorageError::Unavailable（可重试）
//   57P01..03 admin_shutdown 等   → StorageError::Unavailable
//   08000 / 08006 connection_*    → StorageError::Unavailable
```

`is_retryable` 需要新增对 PG `40001` / `40P01` / `08xxx` 的识别——否则 publish flow 的重试器在 PG 下不会重试可恢复错误，导致 false-negative。

`classify_sqlite_error` 重命名 `classify_db_error`，内部按 `sqlx::Error::Database(db_error)` 的 `db_error.code()` 走两套分支：SQLite 现有逻辑保留，PG 走 SQLSTATE。

### 8.3 PostgreSQL 测试容器

- `testcontainers-rs` 拉起一次性 PG 容器
- **per-module shared container**（容器启动成本 ~2s，per-test 拉起不可取）
- **per-test 独立 schema + 独立 pool**

  `SET search_path = 'test_xxx'` **是连接级状态**：sqlx `Pool` 内部可能有多条连接，单次 `SET` 命中其中一条，后续 acquire 不同连接时 search_path 会复位到默认 `public` ——**测试隔离假象**。

  正确做法（二选一）：

  1. **URL 参数固化**（首选）：每个 test 构造独立 URL，把 schema 嵌入 connect option：

     ```rust
     // 容器 base URL：postgres://postgres:test@127.0.0.1:5432/postgres
     let schema = format!("test_{}", uuid::Uuid::new_v4().simple());
     // 用 admin pool 先 CREATE SCHEMA
     sqlx::query(&format!("CREATE SCHEMA \"{schema}\"")).execute(&admin_pool).await?;
     let url = format!(
         "postgres://postgres:test@127.0.0.1:5432/postgres?options=-c%20search_path%3D{schema}"
     );
     let pool = PgPoolOptions::new().max_connections(4).connect(&url).await?;
     // 此 pool 所有连接都自动 SET search_path
     ```

  2. **`after_connect` hook**：

     ```rust
     PgPoolOptions::new()
         .after_connect(move |conn, _| {
             let schema = schema.clone();
             Box::pin(async move {
                 sqlx::query(&format!("SET search_path TO \"{schema}\"")).execute(conn).await?;
                 Ok(())
             })
         })
         .connect(&base_url).await?;
     ```

  per-test 结束后由 fixture 调 `DROP SCHEMA ... CASCADE` + `pool.close()` 清理。决议采用方式 1，更简单、可在多线程 runtime 下健壮。
