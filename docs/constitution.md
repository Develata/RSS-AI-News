# RSS-AI-News 工程宪法

## 1. 适用范围

本宪法适用于 `RSS-AI-News` 新 Rust 仓库的全部设计、实现、重构、迁移、评审与运维决策。

本宪法的目标不是替代判断，而是在高质量判断成立的前提下，约束工程实现忠实执行骨架级决策，避免系统在后续演化中被局部便利、短期需求或惯性改写。

## 2. 总纲

### 2.1 固定设计顺序

任一正式设计任务必须严格按以下顺序执行：

1. 定义总骨架与边界
2. 列出模块清单
3. 细化实现逻辑

禁止跳过前项直接进入后项。

### 2.2 骨架优先

系统必须先有总骨架，再有模块，再有实现。  
任何局部功能只能填入既定骨架，不得反向塑造骨架。

### 2.3 稳定性优先

系统优先保持整体结构长期稳定，而不优先追求局部极致最优。  
模块允许替换，实现允许迭代，但主骨架不得被日常功能迭代持续侵蚀。

### 2.4 优先级排序

当多个目标发生冲突时，必须按以下顺序作取舍：

1. 正确性 / 功能实现
2. 可用性 / 使用体验
3. 根基兼容性
4. 可维护性 / 可诊断性
5. 性能
6. 内存占用
7. 外存占用
8. 其它次级因素（如组件复用、工程复杂度控制等）

低优先级目标不得破坏高优先级目标。

### 2.5 根基兼容性的定义

“根基兼容性”仅指对系统底层长期稳定生态的兼容能力，以及对未来一至两年内可能变化的根基外部参数的适应能力，例如：

- CA 证书体系
- TLS / HTTP 网络协议行为
- 时区配置与时区数据库
- Git / GitHub 生态接口
- Rust 语言生态与关键依赖生态

## 3. 骨架约束

### 3.1 本体优先

系统定义应围绕本体对象、核心关系和能力轴，而不是围绕首版功能清单。

对本项目，本体对象至少包括：

- 订阅源
- feed 条目
- 文章正文
- AI 结果
- 发布快照
- 发布产物

### 3.2 四层架构 + 对象层

本项目采用“四层架构 + 对象层”的组织方式：

1. 交互壳层
2. 指令接口层
3. 流程协调层
4. 能力执行层
5. 对象层

任何新能力都必须明确自己属于哪一层，禁止跨层混写。

### 3.3 壳核分离

CLI / UI / Web 壳层只负责转译与呈现，不能直接承载核心业务逻辑。  
核心逻辑不得依赖具体交互形态。

### 3.4 单一真相源

对任何核心对象、核心状态与核心配置，必须明确唯一可信来源。  
内存缓存、界面状态、临时文件不得与持久真相源并列为最终依据。

### 3.5 模块替代优先于流程改写

系统优先支持模块替代，而不是持续修改主流程。  
新增支持应优先表现为新增平级模块，而不是侵入既有主干。

### 3.6 外部依赖通过兼容层进入

所有外部环境依赖必须通过兼容层或适配层进入系统。  
核心逻辑不得直接绑定环境细节。

## 4. 蓝图约束

### 4.1 蓝图必须可施工

任何架构输出都必须细化到实现逻辑，不允许停留在概念层。

一个可施工的工程蓝图至少必须明确：

- 模块职责
- 调用关系
- 输入输出
- 状态变化
- 错误处理
- 配置入口
- 生命周期
- 扩展点
- 替换点
- 性能关键路径

### 4.2 高层到低层必须连续

高层骨架、模块边界与实现逻辑之间必须连续。  
不允许实现阶段临时发明破坏骨架的新结构。

## 5. 运行可靠性约束

### 5.1 失败优先

系统设计时不能只定义成功路径，还必须优先定义失败路径。  
任何核心流程在进入实现前，都必须明确：

- 失败条件
- 失败传播方式
- 回退策略
- 重试边界
- 用户可见结果

### 5.2 可观测性内建

日志、错误码、状态追踪、关键事件记录与性能指标采集必须作为架构内建能力进入骨架。  
不能依赖事后补日志。

### 5.3 验证先行

任何核心骨架、核心流程、核心边界在进入大规模实现前，都必须有对应验证方式。  
若一个原则无法被验证，则该原则在实现中极易失效。

### 5.4 版本责任

任何核心接口、核心数据模型、核心配置模型一旦变化，都必须回答：

- 旧版本如何兼容
- 现有数据如何迁移
- 失败后如何回退

凡沉淀到磁盘、数据库、缓存、同步链路或导入导出格式中的结构，都负有版本责任。

### 5.5 幂等与并发一致性

任何可能被重复执行、重复投递、重复恢复执行的核心流程，都必须具备幂等性或显式去重机制。

任何核心状态在被多个流程同时读取、修改、同步或回写时，都必须明确：

- 谁先
- 谁后
- 谁覆盖谁
- 冲突如何解决

## 6. 运行裁量约束

### 6.1 默认保守

在信息不足或不确定性较高时，默认选择更保守、更稳定、更容易回退的方案。

### 6.2 退出路径

系统不仅要定义对象如何产生，也必须定义对象如何停用、删除、迁移、失效和清理。  
任何可被创建的核心对象，都必须有清晰退出路径。

## 7. 治理约束

### 7.1 骨架变更必须审批

任何骨架级变更都必须先提交分析报告，再经管理员 / USER 明确批准，方可执行。

未经审批，不得擅自修改：

- 主骨架
- 核心边界
- 核心对象关系
- 主能力轴
- 关键接口结构

### 7.2 证伪即退出

任何方向、能力轴、抽象、边界划分或骨架判断，一旦经分析被认定为错误、失效或已被证伪，就必须立即退出。

### 7.3 决策允许复核

任何骨架级判断都不因审批地位而自动免于复核。  
只要存在充分理由认为该判断可能失误、偏颇、证据不足或忽略了关键代价，就必须允许提交高质量复核报告进行反证审查。

## 8. 对本项目的直接推论

对 `RSS-AI-News` 而言，以下能力必须被视为骨架级能力，而不是可有可无的后续优化：

- 状态机驱动
- 租约化任务领取
- 发布快照
- 回放能力
- 版本化规则与 prompt
- 幂等插入与重复发布防重
- 失败路径、日志、指标与验证

## 9. 结论

本宪法是本仓库的最高工程约束。  
任何设计、实现或重构都必须能够回答：

- 是否忠于系统本体
- 是否污染主骨架
- 是否破坏了单一真相源
- 是否削弱了根基兼容性
- 是否损害了可维护性与可诊断性

如果答案不成立，则该方案不得进入主干。
