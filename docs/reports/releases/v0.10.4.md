- 状态：tag 前（发版准备）；post-release 证据待回填
- 目标 tag：`v0.10.4`
- 日期：2026-11-21
- 范围：`v0.10.3..v0.10.4`

## 核心交付

正确性：

- **一次可重试失败不再中止整轮 extract。** v0.10.3 在一批里出现 retryable 失败（超时 / 5xx / 连接失败）后立即结束本轮
  （日志 "retryable failures in batch; deferring re-claim to next run"），因为被释放的行马上又能被领取。2026-11-20 18:20 与
  18:30（北京时间）同一篇文章（feed_entry_id 1803140）连续超时，`batch_size = 1` 时两轮都只跑了一批，其后的健康条目未被抽取。
  现在：
  - 新列 `feed_entries.next_attempt_at`（迁移 0007，两方言）。retryable release 在释放 lease 的同一条 owner-guarded UPDATE 里写入
    冷却截止点：按刚失败的那次尝试 10 / 20 / 40 / 80 min，上限 2 h。重试预算、最后一次尝试转 `failed`、预算耗尽 sweep 不变。
  - claim 在 `LIMIT` 之前跳过冷却中的行，冷却行不占批次名额；是否到期按每次 claim 的时刻判断。
  - 循环继续领取其他可领取行，直到 claim 为空或达到 `max_batches`。
  - 同一 run 不重试已经尝试过的条目：claim 排除本 run 已领取、且未确认终态成功的 id。这也覆盖 release 落空
    （lease 过期被并发 run 回收，owner guard 拦下 release）和并发 backfill reset 的情形。跨 run 的过期 lease 恢复不变。
  - 冷却从 release 时刻起算（策略链耗时不缩短冷却），`updated_at` 记同一时刻。
  - 永久失败、summary fallback 不变；backfill reset 清空 `next_attempt_at`。
- **SQLite 上 `feed_entries` 的时间比较按时刻而非文本。** sqlx 以小数位数可变的 RFC3339 TEXT 存时间，同一秒内文本序与时刻序不同
  （`…00.12Z` 排在 `…00.1Z` 之前）。claim、lease 回收、预算耗尽 sweep 的 lease 判断与冷却判断改用 `julianday()`；写入的
  截止点与 lease 转 UTC 并向上取整到毫秒，比较时刻向下取整到毫秒，因此不会提前判定（最多晚约 2 ms）。`julianday()` 解析不了
  的旧文本回退到原先的文本比较。PostgreSQL 不变。其余 lease 表（article_ai_results、publish_records、reindex_jobs、
  decision_results）未改。

可观测性：

- `ExtractSummary.retryable_deferred` 含义改为"本 run 有 retryable 失败，重试推迟到之后的 run"，不再表示"循环因此提前结束"，
  可与 `max_batches_reached` 同时为 true。旧日志行换成 "retryable failures; retries deferred to later runs"。
- claim 出错时，`run_completed` 事件也带完整计数，并附 `claim_error`。

内部：

- `FeedEntryRepository::claim_pending_fetch` 增加 `exclude_ids`，`release_retryable_failure` 增加 `retry_at`；`ExtractDeps` 增加
  可注入的 `clock`（生产为系统时钟）。`tools/perf/query_plans.py` 按新参数绑定。

## 已知限制（未在本版处理）

- claim 仍按 `discovered_at` 从旧到新。可领取的旧积压大于 `batch_size × max_batches` 时，新条目仍可能整轮排不上，进而落到发布
  窗口之外；冷却修复不保证新文章能被发布。测试 `oldest_first_backlog_still_starves_fresh_entries_under_cap` 记录了这一点，
  有界 fresh-first 的提案见 [plan/02 §5.3](../../plan/02-extract.md)（未实现）。
- `ai-run` 仍在出现 retryable 失败后停止 claim（`flows/ai_run/mod.rs`），本版未改。

## 升级与行为变更

**有数据库迁移**：`0007_feed_entry_retry_cooldown`，两方言，只加一列可空的 `next_attempt_at`。任何写命令首次运行时自动应用，也可先
`migrate run`。配置文件格式不变。

| 变更 | 影响 |
|---|---|
| 迁移 0007 | 现有行 `next_attempt_at` 为 NULL，立即可领取；已是 `failed` 的行保持不变 |
| batch 内有 retryable 失败 | 原先：本轮结束；现在：该行冷却，本轮继续领取其他行 |
| 冷却中的行 | 截止点之前不被 claim，也不占批次名额 |
| `retryable_deferred` | 含义见上，可与 `max_batches_reached` 同时为 true |

**回退**：数据库一旦应用 0007，v0.10.3 的二进制会因"已应用但源码中不存在的迁移"拒绝运行。回退前先用本版执行 0007 的
down 迁移（删除该列），再换回 v0.10.3。

## 跨模型审查

Codex（gpt-6.2-astra，effort high），三轮：

- 第一轮审查 `a047120..9856680`，2 个 BLOCKER：
  - SQLite 冷却按文本比较，同一秒内会提前或推迟：改为 `julianday()`。
  - lease 被并发 run 回收后，原 run 可再次领取同一行：claim 增加本 run 的排除列表。
  - SHOULD_FIX 全部处理（claim 出错时的事件计数、冷却起算时刻、查询计划工具、测试确定性、fresh-first 提案）；
    "release 冲突时不应置位 `retryable_deferred`" 未采纳，因为冲突时重试同样推迟到之后的 run。
- 第二轮审查 `384897f`，2 个 BLOCKER：
  - `julianday()` 舍入到毫秒，可提前约 300 µs 领取：截止点向上、比较时刻向下取整到毫秒。
  - 以 run 开始时刻判断到期会漏掉 run 期间到期的工作：改为每次 claim 时判断，排除列表单独保证同 run 不重试。
  - SHOULD_FIX：排除列表随处理量平方增长（成功行移出）、`+15:00` 偏移不可解析（写入前转 UTC）、`retryable_deferred`
    文案；为测试加入可注入时钟。SQLite lease 比较按文本这一基线缺陷另行修复（`e66206b`）。
- 第三轮审查 `384897f..e66206b`，2 个 BLOCKER：
  - 旧数据中 `julianday()` 不可解析的 lease 会永久跳过：四处时间谓词回退到文本比较。
  - 版本号仍为 0.10.3：由本次发版准备解决。
  - SHOULD_FIX：亚毫秒测试补上能区分 claim 侧取整的边界，PG 改走 release 写入；`updated_at` 与截止点同一时刻；文档更正。
    "曾运行中间版本 `384897f` 的库可能提前重试"不适用：该版本从未推送或部署。
  - 记录不改：失败密集时排除列表的累计传输约 F(F−1)/2（F 为本 run 失败数）。
- 第三轮修复（`9866673`）没有再送审。
